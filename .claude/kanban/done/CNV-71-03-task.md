### Гибридная проверка воркера при создании конвертации

**Criticality:** High

**TAGS:**
- feature

**Description:**
Часть эпика CNV-71. Требует завершённой CNV-71-02 (валидация пар уже переведена на каталог).

**Problem:**
Сейчас наличие воркера для формата определяется через `worker_capabilities` в момент построения матрицы форматов, а не в момент создания конвертации; отдельной обработки «воркер такого типа никогда не был» и «воркер временно offline» нет.

**Impact:**
Без гибридной проверки и протухания задач удаление seed-строк (CNV-71-04) может либо принимать неисполнимые задачи навечно, либо необоснованно отказывать по формату, для которого воркер когда-либо был.

**Recommendation:**
В `ConversionManager::createConversion()`: пара валидируется по каталогу; затем — если строки воркера нужного типа в `worker_capabilities` нет вообще → немедленный отказ с понятным текстом (не «формат не поддерживается», а «конвертация временно недоступна»); если строка есть → задача принимается и ставится в очередь. Реализовать НОВУЮ механику протухания принятой, но никем не взятой задачи (сейчас такая запись висит в стриме вечно) — см. открытый вопрос в эпике CNV-71. Не путать с reclaim (`workers/gateway/reclaim.py:29-50`) — он про уже заклеймленные записи исчезнувшего консьюмера, а не про никем не взятые.

**Открытый вопрос (решить при старте, подтвердить у пользователя перед реализацией):** конкретное значение таймаута ожидания воркера и что происходит по его истечении. Предложение по умолчанию — таймаут в env, дефолт 15 минут, по истечении конвертация переходит в failed с отдельным кодом причины.

**Acceptance Criteria:**
- `createConversion()` при отсутствии строки воркера нужного типа в `worker_capabilities` сразу отказывает с понятным текстом («конвертация временно недоступна»)
- При наличии строки воркера (даже offline) задача принимается и ставится в очередь
- Реализована новая механика протухания принятой, но никем не взятой задачи, с таймаутом из env
- Tests/QA green: `make phpstan`, `make cs-check`, тесты — см. CLAUDE.md

**Decisions:** *(resolved grooming questions — keep on the card after `todo/` so the rationale survives)*
- Критерий «воркер есть» — наличие строки в `worker_capabilities`, не статус alive — подтверждено пользователем 2026-08-04
- Гибрид: строка есть (offline) → ждать с таймаутом; строки никогда не было → немедленный отказ — подтверждено пользователем 2026-08-04

**Execution Log:**
- Гейт `existsForWorkerType` — в `createSingleHop`/`createChain`/`retryConversion`, до любых quota/S3-эффектов → 503 `worker_unavailable`, текст «Конвертация временно недоступна». Инъекция репозитория в прод-контейнере подтверждена через `debug:container`.
- Протухание: свип в `workers/gateway/expiry.py` — «никому не доставлялась» = backlog строго за `last-delivered-id` группы, возраст из ms-префикса id записи; перед действием повторная проверка `last-delivered-id`, `XDEL` только после успешного ответа PHP.
- Эндпоинт `POST /api/v1/internal/worker/expire` → статус `Expired` (значение уже было в enum), возврат квоты/баланса, идемпотентность по всем терминальным статусам.
- Таймаут `WORKER_CLAIM_TIMEOUT_MINUTES=60` в корневом `.env`, прокинут в `ws-gateway`.
- Гонка возвратов: guard в `ConversionResultPersister` — под `LockMode::PESSIMISTIC_WRITE`; до этого два конкурентных вызова могли вернуть деньги дважды.
- Крайние случаи: неразбираемый payload → в `conv.dead` + ERROR-лог, не тихий дроп; 404 от `/expire` → терминально, запись удаляется; 5xx/сеть → ретрай.
- Фронтенд: `expired` с текстом про возврат оплаты; клиентский кап опроса больше не выставляет ложный `failed`, показывает «ещё в очереди» со ссылкой на историю.
- Ограничение: ветка «строки воркера нет» недостижима e2e до CNV-71-04 (есть `__seed__`-строки); покрыта юнит- и функциональным тестом с откатом транзакции.
