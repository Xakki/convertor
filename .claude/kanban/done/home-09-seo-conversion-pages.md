### SEO-лендинги под конкретные пары конвертации (`/convert/{source}-to-{target}`)

**Criticality:** Medium

**TAGS:**
- feature
- frontend
- backend
- seo

**Description:**
Часть эпика [[home-00-epic]]. Выполняется последней в цепочке — зависит от
[[home-07-i18n]] (EN/RU-тексты), [[home-01-header-nav]] (хедер получает
пункт «Конвертации»), [[home-03-conversion-variants]] (данные о вариантах
конвертации) и [[home-04-format-info-examples]] (реальные примеры из S3,
переиспользуются на странице пары).

Сейчас единственная точка входа в конвертацию — `GET /`
(`App\Controller\Web\HomeController`, `app-symfony/src/Controller/Web/
HomeController.php:21`, роут `app_home`) с универсальной формой, где
исходный и целевой форматы выбираются пользователем. У сервиса нет ни одной
страницы, заточенной под конкретную пару source→target (например «PDF в
Word», «PNG в JPG») — а именно такие пары обычно являются точкой входа из
поисковой выдачи для конверторов файлов.

Эта подзадача заводит по одной SEO-странице на КОНКРЕТНУЮ пару конвертации:
уникальный URL, H1/title/meta заточены под пару, форма предзаполнена и
зафиксирована на этой паре, есть поясняющий текст и живой пример результата.

**Problem:**
Универсальный `/` не даёт поисковику ничего специфичного проиндексировать
под конкретный запрос вида «convert pdf to word online» — нет уникального
title/H1/URL под пару, весь трафик такого рода упирается в общую форму без
контекста под конкретный сценарий.

**Impact:**
Сервис теряет органический трафик по длинному хвосту запросов
«X to Y converter» — основной канал привлечения для похожих SaaS-конверторов;
конкуренты со страницами под конкретные пары забирают эту выдачу.

**Recommendation:**
- Роут-паттерн `GET /convert/{pair}` (например `App\Controller\Web\
  ConversionPageController`, слаг вида `pdf-to-docx`), где `{pair}`
  парсится в `source` и `target` по разделителю `-to-`. Валидировать пару
  через `App\Service\Conversion\ConversionRegistry::isSupported($source,
  $target)` (`app-symfony/src/Service/Conversion/ConversionRegistry.php:86`)
  — неподдерживаемая или нераспарсиваемая пара → `404` (`NotFoundHttpException`,
  тот же подход, что и в остальных контроллерах проекта).
- Шаблон страницы (например `templates/conversion/pair.html.twig`,
  расширяет `templates/base.html.twig`, переиспользует хедер/футер из
  [[home-01-header-nav]]):
  - Уникальный `<h1>` («Конвертировать {source} в {target}») и `<title>` /
    `meta name="description"` / `<link rel="canonical">`, построенные
    по паре — через i18n-ключи с плейсхолдерами (см. [[home-07-i18n]], EN+RU
    в `translations/messages.{locale}.yaml`, не хардкод).
  - Форма конвертации, ПРЕДЗАПОЛНЕННАЯ и зафиксированная на этой паре:
    source/target НЕ редактируются пользователем (в отличие от универсальной
    формы на `/`) — переиспользовать Alpine-компонент `converterApp()` из
    `conversion/index.html.twig`, но с `source`/`target` заданными из
    роута и заблокированными в UI (не `<select>`, а статичный лейбл + hidden
    input, либо `<select>` с единственной опцией — на усмотрение исполнителя).
    Отправка идёт через тот же `POST /api/v1/convert`, без изменений
    бэкенда сверх того, что уже сделано в [[home-02-text-input]].
  - SEO-текстовый блок, описывающий именно эту конвертацию (что за форматы,
    зачем конвертировать, какие есть нюансы) — контент через i18n-ключи.
  - Пример результата — переиспользовать примеры из S3, заведённые в
    [[home-04-format-info-examples]] (`examples/<category>/…` в бакете
    `${S3_BUCKET_PREFIX}-results`); если для конкретной пары готового
    примера нет — показывать пример категории (source/target формата) без
    блока «нет примера» как основного состояния.
- **Хедер: dropdown «Конвертации»** (координировать с [[home-01-header-
  nav]], не заводить второй независимый компонент навигации) — список ссылок
  на страницы пар. Полная матрица пар (см. ROADMAP.md «Справочные данные» →
  «Матрица поддерживаемых конвертаций») слишком велика для dropdown — решение:
  dropdown показывает КУРИРУЕМЫЙ подсписок — популярные/показательные пары,
  сгруппированные по категории (документы/изображения/аудио/видео/данные/
  разметка), примерно по 2–3 пары на категорию (тот же принцип отбора, что
  и D3 для примеров в [[home-04-format-info-examples]] — не обязательно те
  же самые пары, но тот же дух «по одной-две показательных на категорию»).
  Список пар для dropdown — статичная конфигурация (например константа/enum
  в контроллере или Twig-партиал), не генерируется на лету из полной матрицы.
- Источник данных о форматах/категориях — `GET /api/v1/formats` /
  `App\Service\Conversion\ConversionRegistry` (`api-design`,
  `backend-architecture`), без нового бэкенд-эндпоинта под сами страницы —
  Twig-контроллер читает Registry напрямую (как и остальные Web-контроллеры
  проекта), не через HTTP-вызов к своему же API.
- **Sitemap:** по возможности добавить эти маршруты в `sitemap.xml` (если
  в проекте уже есть генератор sitemap — расширить его; если нет —
  минимальный статичный/сгенерированный `sitemap.xml` со списком URL страниц
  пар, отдаётся отдельным контроллером/роутом). Если полноценный sitemap
  выходит за разумный объём этой подзадачи — зафиксировать это в Execution
  Log как явный follow-up, но URL/H1/title/canonical должны быть в любом
  случае.
- Стек: Twig + Alpine.js + Tailwind CDN, без npm/build (см. правило проекта
  Frontend Rules).
- **Явно вне скоупа этой подзадачи:** SEO-копирайт/keyword-тюнинг текста
  под конкретные поисковые запросы (подбор ключевых слов, объём и качество
  текста для ранжирования, A/B текста и т.п.) — это отдельная последующая
  задача. Здесь делается только СТРУКТУРНАЯ SEO-готовность: уникальный URL,
  семантичный H1, title/meta/canonical, форма под пару, пример результата.

**Acceptance Criteria:**
- `GET /convert/{source}-to-{target}` для поддерживаемой пары (проверено
  через `ConversionRegistry::isSupported`) отдаёт `200` со страницей: H1,
  `<title>`, `meta description`, `<link rel="canonical">` уникальны для
  этой пары.
- `GET /convert/{source}-to-{target}` для неподдерживаемой/нераспарсиваемой
  пары → `404`.
- Форма на странице пары зафиксирована на source/target из URL (не даёт
  пользователю сменить их через UI) и отправляет реальную задачу конвертации
  через существующий `POST /api/v1/convert` — статус/скачивание работают
  как на `/`.
- Страница показывает SEO-текстовый блок (EN+RU через i18n) и хотя бы один
  пример результата (свой для пары либо для категории пары) из
  [[home-04-format-info-examples]].
- В хедере/nav есть dropdown «Конвертации» со ссылками на курируемый
  подсписок страниц пар, сгруппированный по категории — не полная матрица.
- EN+RU переключение локали работает на странице пары так же, как на `/`
  (через [[home-07-i18n]]).
- `sitemap.xml` включает URL страниц пар (если реализовано в скоупе — см.
  Recommendation; иначе явно зафиксирован follow-up в Execution Log).
- Tests/QA green: `make test`, `make phpstan`, `make cs-check`.

**Decisions:**
- Слаг-формат маршрута — `{source}-to-{target}` (например `/convert/pdf-to-
  docx`), разбор по разделителю `-to-`, валидация через `ConversionRegistry::
  isSupported`, невалидная пара → `404`.
- Dropdown в хедере показывает курируемый/популярный подсписок пар,
  сгруппированный по категории (не полную матрицу форматов) — конкретный
  набор пар выбирает исполнитель на этапе реализации по тому же принципу,
  что и примеры в [[home-04-format-info-examples]] (показательность, не
  исчерпывающая полнота).
- Форма на странице пары — source/target НЕ редактируемы пользователем
  (в отличие от универсальной формы на `/`), чтобы страница оставалась
  однозначно про заявленную в title/H1 пару.
- Keyword/контент-SEO тюнинг текста — явный follow-up, вне скоупа этой
  карточки; здесь — только структурная готовность (URL/H1/title/meta/
  canonical/форма/пример).
