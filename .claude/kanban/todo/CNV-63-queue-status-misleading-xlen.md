### `make queue-status` вводит в заблуждение (XLEN вместо backlog); плюс детальный `queue-inspect`

**Criticality:** High

**TAGS:**
- tech-debt
- makefile
- keydb
- observability

**Description:**
Таргет `queue-status` (`workers/Makefile:262-265`) печатает `XLEN` по каждому
стриму `conv.*` — накопительное число записей в стриме за всё время, стримы
не тримятся. Из-за этого «46 в conv.document / 19 в conv.image, число не
меняется 3 минуты» читается как затык очереди, хотя это здоровое состояние
(записи просто не удаляются после обработки).

Диагностика очередей (`XPENDING` по группе, `XINFO GROUPS`, содержимое DLQ)
при этом недоступна через Makefile вообще — только `docker exec ...
keydb-cli` вручную; быстрого способа посмотреть pending/DLQ через `make` не
было.

**Problem:**
Реальный backlog (сколько задач реально ждут/висят) виден только через
`XPENDING` на consumer-group. `queue-status` его не показывает, что при
диагностике 2026-08-04 привело к ложному подозрению на «зависшие очереди»
(на деле джоба 66 отработала за 31 мс, просто с 6-минутной задержкой
ретраев — см. CNV-65). Отсутствие детального инструмента (`XINFO GROUPS`,
`XPENDING` по каждой записи, дамп DLQ) замедлило разбор — пришлось вести
диагностику по метрикам Prometheus.

**Impact:**
Высокий — основной диагностический инструмент показывает не ту метрику,
провоцирует ложные incident-репорты и трату времени на поиск несуществующего
затыка.

**Recommendation:**
1. Переделать `queue-status` (`workers/Makefile:262-265`): вывод ведёт с
   реальным backlog по каждому стриму `conv.*` — pending на consumer-group
   (`XPENDING`), max-idle (мс) самой старой pending-записи, размер DLQ
   (`conv.dead`, см. ниже). `XLEN` остаётся справочной/вторичной колонкой с
   явной пометкой «накопительное, не backlog».
2. Не изобретать формулы заново — переиспользовать то, что уже считает
   `workers/metrics_exporter/exporter.py`: `r.xinfo_groups(stream)` (:175),
   `r.xpending_range(stream, name, min="-", max="+", count=1)` для idle
   самой старой pending-записи (:201), длина DLQ через
   `r.xlen("conv.dead")` (:223-236).
3. Добавить отдельный детальный таргет `queue-inspect` (опциональный фильтр
   `STREAM=conv.image`), печатающий по каждому стриму `conv.*` (или по
   выбранному): полный `XINFO GROUPS`, детальный `XPENDING` (ID записей,
   idle-время, delivery count) и содержимое DLQ (`conv.dead`).
4. В репозитории нет каталога `scripts/` и `keydb-cli` используется только
   из `workers/Makefile` — реализация обоих таргетов остаётся в
   `workers/Makefile` (eval-скрипты/lua или аналог), без нового каталога.
5. DLQ-стрим — `conv.dead` (`workers/gateway/keydb.py:49`), а не
   `conv.result.dead` — исправить любые упоминания `conv.result.dead` как
   «текущего DLQ» (устаревшее имя, см. CNV-68).
6. `##`-описания обоих таргетов в `workers/Makefile` — терсе, стандартные
   сокращения (правило проекта: справка Makefile = документация).

**Acceptance Criteria:**
- `make queue-status` для каждого стрима `conv.*` печатает первым pending
  (XPENDING по consumer-группе) и max-idle (мс) самой старой pending-записи;
  XLEN показывается отдельной колонкой с явной пометкой
  «cumulative, not backlog».
- Размер DLQ (`conv.dead`, XLEN) виден в выводе `queue-status`.
- `make queue-inspect` (опционально `STREAM=conv.<type>`) печатает по
  каждому стриму (или по выбранному): полный `XINFO GROUPS`, детальный
  `XPENDING` (ID + idle + delivery count) и содержимое `conv.dead`.
- Ни один из двух таргетов не ссылается на `conv.result.dead` как на DLQ —
  везде `conv.dead`.
- Оба таргета имеют терсе `##`-описания в `workers/Makefile`.
- Ручная проверка на dev-стенде: вывод `queue-status` не показывает
  ложный backlog при пустых consumer-группах (pending=0), даже если XLEN
  стримов растёт.

**Decisions:**
- 2026-08-04: объединено с CNV-64 (карта удалена, содержание перенесено
  сюда) — обе задачи про диагностику очередей и делаются вместе одним
  изменением Makefile.

**Контекст:** найдено в ходе диагностического прогона 2026-08-04 (разбор
ложного репорта «зависшие очереди»; на деле ничего не стояло, джоба 66
завершилась за 31 мс полезной работы при 6 мин wall-clock из-за ретраев).

Отдельно замечено при том же прогоне: Graylog MCP хардкодит `source`+`message`
в выдаче, поэтому структурные поля (`context_error`, `context_exception`)
через агента не читаются, а выданный Graylog API-токен ограничен на поиск
(403) — это заблокировало чтение точного текста worker-исключения. Стоит
учитывать при доработке диагностики.
