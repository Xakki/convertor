### Dashboard: персональные API-токены для публичного API

**Criticality:** High

**TAGS:**
- feature
- api
- dashboard
- authentication

**Description:**
Добавить в `/dashboard` управление персональным API-токеном для публичного API:
выпуск, безопасное отображение статуса и отзыв. Задача имеет высший продуктовый
приоритет среди новых карточек.

**Problem:**
У пользователя нет персонального API-токена и способа самостоятельно управлять
доступом программного клиента. Существующий `WORKER_API_TOKEN` — внутренний
статический секрет воркеров и не может использоваться как пользовательский ключ.

**Impact:**
Публичный API нельзя безопасно использовать из внешних интеграций, а пользователь
не может немедленно отозвать скомпрометированный доступ.

**Recommendation:**
Создать отдельную сущность и миграцию пользовательского токена, хранить только
невосстановимый материал секрета, добавить authenticator в allowlisted
пользовательскую API-поверхность и блок управления в dashboard. Секрет показывать
только один раз при выпуске; последующее получение возвращает только metadata.

**Acceptance Criteria:**
- `ROLE_USER` выпускает и отзывает персональный токен в `/dashboard`; plaintext
  показывается только в ответе на выпуск и не восстанавливается впоследствии.
- Каждый зарегистрированный пользователь любого плана может иметь не более трёх
  активных именованных токенов; выпуск четвёртого отклоняется предсказуемой ошибкой.
- Секрет, Authorization header и его производные не попадают в БД в открытом
  виде, логи, exception text, последующие JSON-ответы и UI.
- Токен немедленно перестаёт работать после отзыва; гость/аноним не может
  выпускать, читать metadata или отзывать токены.
- Bearer-токен действует только на утверждённой allowlisted пользовательской API
  поверхности и не открывает `/api/v1/admin`, `/api/v1/worker`, `/api/v1/internal`
  и auth-management endpoints.
- Через токен сохраняются owner checks, quota, billing и rate limits JWT-потока.
- Есть functional/unit tests для valid/revoked/malformed token, изоляции владельца,
  гостевого запрета, coexistence с JWT, запрета внутренних маршрутов и отсутствия
  plaintext после выпуска; `make phpstan`, `make cs-check` и профильный PHPUnit
  зелёные.

**Decisions:** *(resolved grooming questions — keep on the card after `todo/` so the rationale survives)*
- `WORKER_API_TOKEN` остаётся внутренним fail-closed секретом и не меняется.
- 2026-08-14: для MVP выбраны несколько именованных персональных токенов с
  независимым отзывом; plaintext каждого показывается только при выпуске. Лимит —
  три активных токена для каждого зарегистрированного пользователя независимо от
  плана.
- 2026-08-14: токен — opaque random bearer без обязательного TTL, с безопасным
  prefix, label и `last_used_at`; ротация выполняется выпуском нового и отзывом
  старого токена.
- 2026-08-14: allowlist токена ограничен публичными conversion, quota, history,
  download и preview маршрутами; admin/worker/internal/auth запрещены. Отдельный
  per-token rate limit не вводится: действуют существующие user/IP лимиты.
- Гости остаются `ROLE_GUEST`; их quota и запреты AI/video не обходятся токеном.
- Зависимые API-аудит и вкладка истории оформлены отдельной CNV-84.
