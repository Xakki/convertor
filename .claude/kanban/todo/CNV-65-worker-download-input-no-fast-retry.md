### Воркер не ретраит скачивание входного файла — fail сразу, повтор только через idle-reclaim (~2 мин)

**Criticality:** Medium

**TAGS:**
- tech-debt
- workers
- reliability
- queue

**Description:**
`_download_input` в `workers/common/ws_client.py:1167-1180` при транзиентной
сетевой ошибке сразу отдаёт fail — нет `try/except`, нет retry. Исключение
пробрасывается в `_run_job` (~:1079) и становится retryable-fail, повтор
задачи происходит только через idle-reclaim gateway, что превращает быстрые
транзиентные сбои в многоминутные задержки.

**Problem:**
Наблюдалось на джобе `1785835446004-0` (диагностический прогон 2026-08-04,
тип `image`): 3 неудачные попытки скачивания входного файла, в итоге 6 минут
wall-clock вместо 31 мс полезной работы. Изначально это читалось как
«зависшая очередь» (см. CNV-63), хотя на деле — цепочка fail → ожидание
idle-reclaim → retry. Reclaim при этом настроен ПО ТИПАМ
(`workers/gateway/config.py:95-104`):
`RECLAIM_IDLE_MS_DOCUMENT=300000`, `_IMAGE=120000`, `_AUDIO=300000`,
`_VIDEO=600000`, `_DATA=180000`, `_AI=300000` (резолвится через
`reclaim_idle_ms_for()`) — наблюдённый случай — `image` (120с × 3 ретрая).

Отдельно (диагностика uBook, см. CNV-66): `_download_input` использует
общий `httpx.AsyncClient()`, созданный на `:1161` БЕЗ явного timeout —
значит действует httpx-дефолт **5.0 с**. `_upload_large` (`:1203`) рядом
задаёт явный `httpx.Timeout(30.0, read=300.0)` — скачивание входа сегодня
жёстче лимитировано, чем загрузка результата. Тот же дефолт 5.0 с действует
и на `register` (`:804`).

**Impact:**
Средний — транзиентные сетевые сбои превращаются в многоминутные задержки
обработки, воспринимаемые как затык очереди.

**Recommendation:**
1. Добавить ограниченный быстрый retry с коротким backoff внутри
   `_download_input` (`workers/common/ws_client.py:1167-1180`) на
   транзиентные ошибки скачивания — по образцу уже существующего backoff в
   `_register()` (~:779-823, константы `_REGISTER_MAX_ATTEMPTS`/
   `_BACKOFF_BASE_S`/`_FACTOR`/`_JITTER_S` — :59-60). Общего retry-хелпера в
   `workers/common/` нет — сознательно НЕ выносим его сейчас, retry остаётся
   локальным в `_download_input` (см. Decisions).
2. Задать `_download_input` явный `httpx.Timeout` (ориентир: connect ~10 с,
   read ~60 с) вместо неявного дефолта 5.0 с.
3. После исчерпания попыток fail отдаётся так же, как сегодня (без
   бесконечного retry) — idle-reclaim остаётся страховкой на случай, если
   быстрый retry не помог.
4. Пересмотреть per-type `RECLAIM_IDLE_MS_*` (`workers/gateway/config.py:
   95-104`) — теперь, когда транзиентные сбои чинятся быстрым retry внутри
   воркера, оценить, нужно ли снижать какие-то значения (особенно `_IMAGE`).

**⚠ Важная оговорка (из диагностики CNV-66):** одного увеличения timeout
НЕДОСТАТОЧНО. Наблюдённые зависшие сессии простаивали все 30 с без единого
байта от сервера (TLS-хендшейк проваливался на аплинке uBook, см. CNV-66) —
job реально восстанавливался только НОВЫМ соединением ~2 мин спустя (через
idle-reclaim). Поэтому retry обязан открывать НОВОЕ соединение (новый
`httpx.AsyncClient`/новый TLS-хендшейк), а не повторно использовать тот же
залипший stream — иначе retry будет просто ждать тот же таймаут повторно.

**Acceptance Criteria:**
- `_download_input` делает ограниченное число попыток (например, 3) с
  коротким экспоненциальным backoff + jitter на транзиентные ошибки
  (сетевые/timeout/5xx), константы — локальные аналоги
  `_REGISTER_MAX_ATTEMPTS`/`_BACKOFF_BASE_S`/`_FACTOR`/`_JITTER_S`.
- `_download_input` задаёт явный `httpx.Timeout` (connect ~10 с, read ~60 с)
  вместо дефолтных 5.0 с.
- Каждая retry-попытка открывает новое соединение (новый TLS-хендшейк), а
  не переиспользует залипшее — иначе retry не спасает от сценария CNV-66.
- После исчерпания всех попыток `_download_input` пробрасывает ошибку так
  же, как сегодня (job помечается failed тем же путём) — без бесконечного
  retry.
- Тест покрывает: (a) успех со 2-й попытки после 1 транзиентного сбоя,
  (b) fail после исчерпания всех попыток.
- Значения `RECLAIM_IDLE_MS_*` в `workers/gateway/config.py` пересмотрены;
  по каждому — либо оставлено как есть с однострочным обоснованием, либо
  изменено с указанием нового значения и причины.
- В `workers/common/` НЕ появляется новый общий retry-хелпер — retry-логика
  остаётся локальной в `_download_input` (осознанное решение, не тех.долг).

**Decisions:**
- 2026-08-04: retry скачивания и пересмотр reclaim-таймаутов делаются
  вместе, одной картой (не разделять). Retry — локально в
  `_download_input`, по образцу backoff из `_register()`; общий
  retry-хелпер в `workers/common/` сейчас НЕ выделяется.
- 2026-08-04: добавлен явный `httpx.Timeout` на `_download_input` (сейчас
  неявный дефолт 5.0 с) — найдено при диагностике CNV-66; см. оговорку выше
  про обязательность нового соединения на retry.

**Контекст:** найдено в ходе диагностического прогона 2026-08-04 (джоба
1785835446004-0). Сетевая причина зависаний — см. CNV-66.
