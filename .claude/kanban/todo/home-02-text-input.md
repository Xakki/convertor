### Ввод текста без файла (paste-режим конвертации)

**Criticality:** Medium

**TAGS:**
- feature
- frontend
- backend

**Description:**
Часть эпика [[home-00-epic]]. Выполняется после [[home-07-i18n]] и
[[home-01-header-nav]] в цепочке зависимостей эпика.

Сейчас `conversion/index.html.twig` принимает вход ТОЛЬКО через drag&drop
файла: исходный формат авто-определяется из расширения загруженного файла
(read-only селект), затем `POST /api/v1/convert` (multipart `FormData`: поле
`file`, `to_format`, опционально `ocr`) — см.
`app-symfony/templates/conversion/index.html.twig:576-582`,
`App\Controller\Api\ConversionController::convert()`
(`app-symfony/src/Controller/Api/ConversionController.php:95`).

Эта подзадача добавляет альтернативный режим ввода: пользователь вставляет
(paste) текст напрямую, без загрузки файла — актуально для текстовых
категорий (markup: md/html/rst; данные: csv/json/xml/yaml/toml; документ:
txt) — т.е. форматов, у которых источник — читаемый текст.

**Problem:**
Для конвертации короткого текстового фрагмента (например, markdown-заметки
в HTML/PDF, JSON в YAML) пользователю приходится создавать и загружать
файл — лишний шаг, ухудшающий UX для самого частого сценария лёгких
текстовых конвертаций (тир T1 Light в ROADMAP).

**Impact:**
Точка трения для быстрых текстовых конвертаций; сервис не используется для
сценария «вставил текст → получил результат» без файла.

**Recommendation:**

**Backend — `POST /api/v1/convert` принимает файл ИЛИ текст (взаимоисключимо):**
- `App\Controller\Api\ConversionController::convert()`
  (`app-symfony/src/Controller/Api/ConversionController.php:95`) сейчас берёт
  вход только из `$request->files->get('file')`. Добавить альтернативное
  поле формы `text` (raw-текст, `multipart/form-data` как и сейчас, без
  смены content-type) + `source_format` (расширение/формат исходного
  текста — обязателен именно в text-режиме, т.к. у вставленного текста нет
  имени файла, из которого сейчас деривится source по правилам
  `backend-architecture`).
- Валидация на входе контроллера/DTO: ровно ОДНО из {`file`, `text`} должно
  присутствовать — оба сразу или ни одного → `400 Bad Request` с понятным
  `error`-кодом (см. существующий шаблон ответов в этом же методе —
  `['error' => '...']` + `Response::HTTP_BAD_REQUEST`, следовать `api-design`
  по форме ошибки).
- Для text-режима: `source_format` обязателен, валидируется, что это
  текстовый формат, поддерживаемый реестром КАК ИСТОЧНИК (сверка с
  `App\Service\Conversion\ConversionRegistry::isSupported($sourceFormat,
  $toFormat)` — та же проверка пары, что и для файлового пути, никакой
  отдельной логики совместимости не заводить). Бинарные форматы
  (docx/pdf/изображения/аудио/видео) как `source_format` в text-режиме —
  отклонять с `422` (тем же путём, что и неподдерживаемая пара сейчас).
- Валидация размера текста — по тем же лимитам плана, что и файл (через
  `App\Service\Conversion\ConversionManager` / `assertWithinSizeLimit`-
  аналог, `app-symfony/src/Service/Conversion/ConversionManager.php:158`):
  считать байтовый размер текста как эквивалент размера файла и прогонять
  через ту же проверку квоты/лимита плана (free/paid), не заводить отдельный
  «текстовый» лимит.
- Материализация: сервер (НЕ клиент) заворачивает полученный `text` во
  временный/потоковый файл с нужным расширением (`source_format`) и
  дальше пускает по ТОЙ ЖЕ цепочке, что и загруженный файл —
  `ConversionRequestDTO` → `ConversionManager::createConversion()` →
  `storeInput()` (`ConversionManager.php:281`) → тот же Messenger/Registry
  флоу. **Воркеры не меняются** (правило проекта: воркеры flag-agnostic,
  видят обычный файл в S3-инпуте — как формируется вход, им не видно).
- `App\DTO\ConversionRequestDTO` (`app-symfony/src/DTO/ConversionRequestDTO.php`)
  сейчас типизирован под `UploadedFile $file` жёстко — расширить контракт
  так, чтобы конструктор/фабрика принимала либо `UploadedFile`, либо
  `text + sourceFormat` (например доп. именованный конструктор
  `ConversionRequestDTO::fromText(...)` либо nullable-поля с инвариантом
  «ровно одно из двух» — на усмотрение исполнителя, решить на этапе
  реализации и зафиксировать в Execution Log).
- Обновить OpenAPI-атрибуты метода `convert()` (`#[OA\RequestBody]`,
  `app-symfony/src/Controller/Api/ConversionController.php:66-79`): схема
  `multipart/form-data` должна отражать оба пути (file ИЛИ text+source_format
  — например через `oneOf`/явное текстовое описание в `description`, следуя
  `api-design`), плюс отразить новый `400`-кейс «оба или ни одного».
- Прочитать skill `api-design` (контракт эндпоинта, форма ошибок, версия
  `/api/v1/`) и `backend-architecture` (Registry/Manager-флоу, как сейчас
  деривится source-формат и куда встраивается материализация текста).

**Frontend — переключатель Файл / Текст:**
- В `conversion/index.html.twig` (Alpine-компонент `converterApp()`)
  добавить переключатель режима ввода: «Файл» (текущий drag&drop, без
  изменений) / «Текст» (новый `<textarea>` + явный `<select>` источника —
  ограниченное текстовое подмножество форматов, см. ниже).
- Список исходных форматов в text-режиме — ограниченное подмножество
  текстовых форматов из категорий «Документы» (txt), «Разметка»
  (md/html/rst и т.д.), «Данные» (csv/json/xml/yaml/toml) — см. ROADMAP.md
  «Справочные данные» → «Матрица поддерживаемых конвертаций». НЕ включать
  бинарные форматы.
- Целевой формат — тот же `<select>`, построенный из `GET /api/v1/formats`,
  отфильтрованный по выбранному исходному формату (как в файловом режиме).
- Отправка (`submit()`, сейчас строка ~577): в file-режиме — как сейчас,
  `fd.append('file', this.file)`; в text-режиме — `fd.append('text',
  this.text)` + `fd.append('source_format', this.sourceFormat)`, БЕЗ
  синтеза `File`/`Blob` объекта на клиенте.
- Пустой текст / превышение клиентского soft-limit (например ~1–5 МБ,
  зеркалит серверный лимит плана) блокирует отправку до похода на сервер —
  UX-подсказка, не замена серверной валидации.

**Acceptance Criteria:**
- `POST /api/v1/convert` принимает file-only запрос — работает как раньше
  (без регрессий).
- `POST /api/v1/convert` принимает text-only запрос (`text` + `source_format`
  + `to_format`) и создаёт обычную задачу конвертации, использующую
  существующий пайплайн один-в-один (тот же `Conversion`-entity,
  статус/поллинг/скачивание — код не дублируется).
- Запрос с ОБОИМИ `file` и `text` одновременно → `400` с понятным
  error-кодом; запрос БЕЗ обоих → `400`.
- `source_format` в text-режиме валидируется против реестра как поддерживаемый
  источник; бинарный/неподдерживаемый `source_format` → `422`.
- Размер текста проверяется против лимитов плана (free/paid), как и размер
  файла — не отдельный лимит.
- Переключатель «Файл» / «Текст» на странице; text-режим не ломает
  существующий file-режим; в text-режиме показывается ограниченный текстовый
  список исходных форматов, целевой — отфильтрован через `/api/v1/formats`.
- Статус/поллинг/скачивание результата работают идентично файловому режиму
  (тот же job/`status`/`download` код).
- Пустой текст / превышение клиентского soft-limit блокирует отправку с
  понятным сообщением (через i18n-ключи, см. [[home-07-i18n]]).
- OpenAPI-документация (`/api/doc`) отражает оба входных пути и новый
  `400`-кейс.
- Tests/QA green: `make test`, `make phpstan`, `make cs-check`.

**Decisions:**
- **Заменено (было: client-side synthesis).** Ранее было решено синтезировать
  `File`/`Blob` на клиенте и переиспользовать `POST /api/v1/convert` без
  единого изменения бэкенда. Пользователь пересмотрел это решение: теперь
  бэкенд явно принимает `text`-путь как первоклассный альтернативный вход
  (см. Recommendation выше) — старый подход «клиент притворяется файлом,
  бэк не трогаем» СНЯТ.
- Исходный формат в text-режиме выбирается пользователем явно (не
  авто-детект по содержимому — избыточно для MVP).
- Материализация текста в файл для пайплайна — на СЕРВЕРЕ (не на клиенте),
  чтобы воркеры оставались flag-agnostic и не завязывались на то, как
  именно был получен вход (файл или текст).
