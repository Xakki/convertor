### Drift-тест проверяет матрицу из DEV-базы вместо тестовой

**Criticality:** Medium

**TAGS:**
- tech-debt
- test
- ci

**Problem:**
`workers/tests/test_routing_drift.py` вызывает `docker exec … php bin/dump-matrix.php --json`
БЕЗ установки переменной окружения `APP_ENV=test` (строки 184–186, также путь native php
без флага на 160–164). В результате скрипт читает матрицу из DEV-базы (`APP_ENV` по умолчанию),
а не из тестовой БД.

**Impact:**
1. `make test-php-live` падает на шаге drift-проверки при условии: разработчик добавил миграцию
   на своём хосте, но забыл накатить её на dev-базу. Сами PHPUnit-тесты при этом проходят зелёные
   (тестовая БД мигрирована корректно), но агрегат падает с ошибкой уровня SQL («Unknown column
   status» и т.д.) — потому что drift-тест проверяет dev-БД, а не тестовую.

2. Результат `make test-php-live` зависит от состояния личной dev-базы разработчика, а не только
   от окружения тестов. Это «скрытая зависимость» — нарушает изоляцию тестового контура.

3. Когда появится CI-pipeline, у раннера вообще не будет dev-базы — и drift-шаг либо упадёт
   (попытается подключиться к несуществующей базе), либо потребует поднимать дополнительное
   окружение только для этого шага.

**Recommendation:**
Пересмотреть цель drift-теста:

- **Вариант A** (целевой): drift-тест должен проверять тестовую БД (`APP_ENV=test`). Тогда матрица
  всегда знана (миграции накачаны, seed залит), и результат не зависит от dev-окружения разработчика.
  **Вопрос:** тестовая БД содержит только seed — не потеряется ли смысл проверки реальных
  регистраций рабочих?

- **Вариант B** (явная асимметрия): drift-тест сознательно проверяет dev-БД как «то, что видит
  разработчик», но тогда нужна явная валидация: перед вызовом `dump-matrix.php` убедиться, что
  целевая БД (dev) мигрирована и доступна, иначе выпустить понятную ошибку вместо SQL-уровня
  («DB migrations not applied, run make migrate; use APP_ENV=test for isolated test runs»).

**Acceptance Criteria:**
1. [ ] Выбран подход (A или B)
2. [ ] При выборе A: `dump-matrix.php` вызывается с `APP_ENV=test` в обоих путях (docker exec и native php)
3. [ ] При выборе A: убеждаемся, что seed/миграции тестовой БД достаточны для полноты drift-проверки
4. [ ] При выборе B: перед `dump-matrix.php` добавлена валидация доступности и миграции целевой БД
5. [ ] `make test-php-live` проходит зелено БЕЗ зависимостей от личной dev-базы разработчика

**Open questions:**
1. Должен ли drift-тест ходить в тестовую БД (`APP_ENV=test`), или сознательно проверяет dev как
   «то, что видит разработчик»?
2. Если в тестовую — не потеряется ли смысл проверки, ведь тестовая БД содержит только seed,
   без реальных регистраций воркеров?
3. Нужно ли явно падать с понятным сообщением (e.g. «DB migrations not applied»), если целевая БД
   не мигрирована, вместо текущей ошибки уровня SQL («Unknown column …»)?
