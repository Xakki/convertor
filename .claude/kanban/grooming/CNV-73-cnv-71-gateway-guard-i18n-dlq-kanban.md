**Description:**
Шесть разрозненных находок из работы над эпиком CNV-71, не попавших ни в
одну существующую карточку (сверено с `grooming/` и `todo/`: CNV-60, CNV-63,
CNV-65, CNV-66, CNV-67, CNV-68, CNV-72). Каждая — отдельный чек-лист-пункт,
без общей темы кроме «найдено походя во время CNV-71». Один инструментальный
пункт (6) — не в этом репозитории.

**Problem:**
См. по каждому пункту в Recommendation ниже.

**Impact:**
По пунктам — от «косметика» (1) до «диагностический слепой пункт, который
уже дважды стоил времени в этом эпике» (2). Ни один не блокирует прод.

**Recommendation:**

1. **i18n захардкодил окно ожидания claim'а текстом.** Копирайт
   `poll_gave_up_message`, добавленный в CNV-71-03, буквально пишет
   «до часа» / «up to an hour» — `app-symfony/translations/messages.ru.yaml:106`
   и `app-symfony/translations/messages.en.yaml:110`. Реальное значение —
   env `WORKER_CLAIM_TIMEOUT_MINUTES` (`.env:117`, дефолт `60`), пробрасывается
   в `ws-gateway` через `docker-compose.yml:632`. Сегодня совпадает, но
   молча разойдётся, если переменную поменять. Вынести в
   `%worker_claim_timeout_minutes%`-параметр перевода (Symfony `trans` с
   аргументом) либо явно закомментировать «держать текст синхронно с env
   вручную».

2. **Нет гарда «задеплоенный образ ws-gateway = текущий HEAD».** За время
   эпика бегущий `ws-gateway` дважды случайно оказывался на старом образе
   (один раз на тест-стенде, один раз на dev) — код существовал в репо, но
   ни разу не исполнялся. Единственный существующий инструмент —
   `gateway-verify-code` (`workers/Makefile:98-100`): copy-out
   `dlq_consumer.py` из контейнера и grep по одному конкретному маркеру
   (`DLQ_AUDIT_LOG_MARKER`) — одноразовый ad-hoc чек под конкретный фикс
   CNV-71, не переиспользуемый гард. Раздел «Verify» в скилле
   `image-build-deploy` (шаги health/registration/logs) тоже не сверяет sha
   образа с HEAD. Предложение: печатать git short-sha в стартовом логе
   `ws-gateway` (по аналогии с уже существующим `APP_VER`,
   `docker/workers/gateway.Dockerfile:36-39`, `--build-arg` из
   `workers/Makefile`) + дешёвый `make gateway-verify-sha`, сравнивающий его
   с `git rev-parse --short HEAD`.

3. **Окно «осиротевшей» DLQ-записи между `XACK` и `XDEL`.**
   `workers/gateway/dlq_consumer.py` (`_process_entry`, см. docstring модуля
   `:59-62`): порядок — relay-2xx → `XACK` → аудит-лог → `XDEL`. Если
   consumer падает между `XACK` и `XDEL`, запись остаётся в `conv.dead`
   навечно осиротевшей (уже зафиналена в PHP, но не удалена из стрима) — тот
   самый монотонный-gauge сценарий, что чинили в CNV-71, но в миниатюре.
   Уже осознанно принято и задокументировано в коде (`не разработка
   cleanup-sweep`) — здесь фиксируется только для будущей диагностируемости
   застрявшего алерта `ConvertorDeadLetterGrowing`, отдельного фикса не
   требуется.

4. **Необъяснённый исторический `XDEL` в `conv.dead`.** `XINFO STREAM
   conv.dead` в ходе диагностики показывал `last-generated-id` =
   `1784214466396-0` (2026-07-16) — ПОЗЖЕ, чем единственная сохранившаяся
   запись `1783878917623-0` (2026-07-12, разобрана и удалена в CNV-68). В
   коде нет пути, удаляющего из `conv.dead` (кроме нового `_process_entry`
   XDEL из п.3, добавленного только в CNV-71), а `XTRIM`, если бы
   применялся, снёс бы САМУЮ старую запись (07-12), а не пощадил бы её. Т.е.
   в какой-то момент кто-то вручную `XDEL`'ил более новые записи —
   актёр/причина неизвестны. Ценность низкая, но фиксирует факт: минимум
   одно реальное DLQ-событие на dev было уничтожено без разбора.

5. **401 при скачивании входного файла воркером — root cause не
   диагностирован.** DLQ-запись, разобранная в CNV-68 (`conversionId=6`,
   2026-07-12), — `worker error: Client error '401 Unauthorized' for url
   '.../api/v1/worker/jobs/1783877914562-0/input' (times_delivered=4)`.
   CNV-68 закрыл вопрос диспозиции самой записи (ACKed residue, конверсия
   в БД уже отсутствует, переотправка не нужна) — но НЕ причину 401. CNV-65
   не покрывает: её ретраи — только для транзиентных сетевых ошибок
   (`workers/common/ws_client.py:1167-1180`), а 401 — не транзиентная,
   retry с тем же токеном не поможет. Auth — статичный bearer
   `WORKER_API_TOKEN` через `WorkerAuthenticator`
   (`app-symfony/src/Security/WorkerAuthenticator.php`,
   `app-symfony/config/packages/security.yaml:36-37,84`); `git log` по
   этому файлу и по `WorkerController.php` не показывает изменений auth-пути
   вокруг даты инцидента (ближайший релевантный коммит — `3d660ab`,
   2026-07-08, ДО инцидента, не трогал `WorkerAuthenticator.php`) — то есть
   баг не «уже починен более поздним коммитом», причина осталась
   недиагностированной (вероятно — рассинхрон токена на конкретном
   удалённом воркере в моменте, см. семейство находок CNV-65/CNV-66).
   Инцидент разовый, не повторялся.

6. **Дефект `kanban-move.sh` (плагин, НЕ этот репозиторий).**
   `/home/coder/.claude/plugins/cache/ai-agents-skills/ai-agents-skills/0.2.13/skills/kanban/scripts/kanban-move.sh`
   вызывает `git-move.sh` → `git mv` (`skills/git-move/git-move.sh:50`).
   Эмпирически подтверждено (тестовый repo в scratchpad): если карточку
   отредактировать МЕЖДУ двумя последовательными вызовами `kanban-move.sh`,
   второй `git mv` стейджит СТАРЫЙ индексный blob (содержимое на момент
   первого move), а правка остаётся незастейдженной рабочей модификацией —
   `git commit` после такого move показывает «чистый rename», правка
   «повисает» как `M <файл>» уже ПОСЛЕ коммита. Причина — стандартное
   поведение `git mv` относительно индекса, не баг конкретно в этом скрипте,
   но заслуживает фикса в плагине (например: `git add` файла ПЕРЕД `git mv`,
   если есть unstaged-изменения). Не трогать внутри `convertor` — это
   апстрим-плагин.

**Acceptance Criteria:**
1. `poll_gave_up_message` (ru/en) либо параметризован реальным
   `WORKER_CLAIM_TIMEOUT_MINUTES` (через Symfony trans-параметр), либо
   рядом с текстом оставлен явный комментарий-напоминание держать в синхроне
   с env вручную — на выбор команды при groom.
2. Существует дешёвый способ узнать git-sha образа бегущего `ws-gateway` и
   сравнить с текущим `HEAD` (лог при старте контейнера и/или
   `make gateway-verify-sha`) — решение по конкретной форме принимается при
   groom (см. Open questions).
3. Пункт зафиксирован как есть (уже задокументирован в
   `workers/gateway/dlq_consumer.py` docstring) — отдельного кода не
   требуется, только явная видимость в kanban для будущей диагностики.
4. Пункт зафиксирован как исторический факт без действия (см. Open
   questions — стоит ли вообще держать эту карточку открытой из-за него).
5. Пункт зафиксирован как «historical, root cause not diagnosed, not since
   fixed by a later commit» — если 401 повторится, разбирать заново с этой
   пометкой как отправной точкой, не с нуля.
6. Дефект зафиксирован здесь для истории; фикс (если будет) — в отдельном
   PR апстрим-плагина `ai-agents-skills`, не в `convertor`.
