### uBook периодически не достучивается до публичного API — эпизодические потери TLS-хендшейка на аплинке/NAT uBook

**Criticality:** Medium

**TAGS:**
- infra
- workers
- ubook
- reliability
- observation

**Description:**
Удалённый воркер-хост uBook периодически не может достучаться до публичного
API `convertor.xakki.pro` (`GET /api/v1/worker/jobs/{id}/input`). Диагностика
2026-08-04 опровергла обе исходные версии карты («API-таймаут», «нет следа
на сервере») и локализовала проблему на сетевом пути uBook.

**Problem:**
Топология: uBook → **saNl `95.211.47.43` (nginx stream, SNI-passthrough)** →
saFin:448 → nginx конвертора — это звено раньше не рассматривалось.

Рвётся не TCP-коннект, а **TLS-хендшейк**: воркер падает с
`httpx.ConnectTimeout` внутри `httpcore .../connection.py:156 →
stream.start_tls`. TCP-соединение при этом устанавливается — обрыв дальше,
на этапе TLS.

След на сервере ЕСТЬ (вопреки исходной версии карты): `/var/log/nginx/
stream-sni.log` на saNl фиксирует эти попытки — `sni="" upstream=- sent=0
recv=0 dur=30.000`, т.е. соединение принято, от клиента не пришло ни байта,
закрыто по 30-секундному `preread_timeout`. Привязка точная: время лога
минус `dur` даёт 09:24:06 / 09:26:11 / 09:28:12 — все три момента диспатча
job'ов (3 из 3 совпали).

Масштаб: с egress-IP uBook `176.115.149.140` за сутки **56 из 659** новых
TLS-сессий блэкхолятся (8.5%); у всех прочих клиентов — 4 из ~50 200
(0.008%). Всплески эпизодические: 06:34–06:38, 08:37, 09:07, 09:21–09:28.
Замеры:
- изнутри контейнера воркера: 0 отказов из 120 и из 51 (окно без всплеска);
- с хоста uBook: 4 из 168 (2.4%);
- контроль с saFin по тому же публичному пути: 0 из 145.

**Impact:**
Средний — часть job'ов uBook (~8.5% TLS-сессий в моменты всплесков)
теряют вход и уходят в retry/idle-reclaim (см. CNV-65), удлиняя обработку
на минуты; сам сервис не деградирует, эффект локален для uBook.

**Recommendation:**
Это диагностическая карта, не задача на исправление кода — сетевая причина
вне зоны ответственности проекта (аплинк/NAT/роутер uBook). Клиентский
харденинг (retry + explicit timeout на новое соединение) вынесен в CNV-65.
Здесь остаётся зафиксировать причину и единственный непроверенный root-пункт
(см. Open questions) на случай, если проблема снова обострится.

Наиболее вероятная причина — эпизодические потери на аплинке/NAT uBook
(WSL2 за домашним роутером), бьющие по SYN и по первым байтам данных;
УЖЕ УСТАНОВЛЕННЫЕ соединения продолжают работать (WS-соединение воркера не
рвалось, fluent-bit слал GELF в те же секунды параллельно с провалами).
Между ISP-шейпингом / CGNAT / домашним роутером / WSL2-NAT имеющиеся данные
не различают — нужен дальнейший сбор при следующем всплеске, если он важен.

Исключено по собранным данным (записать явно, не перепроверять без новых
фактов):
- **DNS** — AAAA отсутствуют, 5/5 одинаковых A, `time_namelookup` в норме.
- **MTU/PMTU-блэкхол** — ~170 тел по 221 КБ прошли без единого сбоя, MTU
  1492 выучен корректно.
- **conntrack** — uBook 128/262144, saNl 1961/262144, обе далеко от лимита.
- **Перегрузка saNl** — `ListenOverflows` 0, load1 0.23–0.92.
- **Серверный бан по IP** — по механике он убил бы и живые GELF/WS-потоки,
  чего не наблюдается.

**Acceptance Criteria:**
- Наблюдение остаётся картой-фактом (не задачей на код): причина и
  масштаб (топология saNl→saFin, TLS-хендшейк, ~8.5% сессий uBook в
  моменты всплесков) задокументированы выше и не требуют переисследования
  без новых симптомов.
- Открытый root-пункт (`iptables`/`ipset` на saNl) либо выполнен и его
  результат дописан в карту, либо явно оставлен как открытый — карта не
  закрывается до его выполнения пользователем.
- Если проблема обострится повторно (заметный рост доли отказов с
  `176.115.149.140` или новых egress-IP uBook) — переоткрыть/дополнить эту
  карту новыми данными, а не заводить дубликат.

**Open questions:**
Остаточная непроверенная ветка (открытый пункт, не для агента) — нужна
root-команда на saNl:
`iptables -L -n -v | grep 176.115.149.140` и
`ipset list trusted_ips | grep 176.115.149.140` — проверить, не режет ли
что-то на уровне netfilter именно этот IP эпизодически. Выполнение отдано
пользователю.

**Decisions:**
- 2026-08-04: разделено на две карты — клиентский харденинг (retry +
  explicit httpx timeout на `_download_input`, с оговоркой про новое
  соединение) ушёл в CNV-65; здесь остаётся чистое сетевое наблюдение о
  причине сбоев на стороне uBook. Карта остаётся в `grooming/` — это не
  задача на код, а зафиксированный вывод диагностики + один открытый пункт,
  требующий root-доступа пользователя.

**Контекст:** найдено в ходе диагностического прогона 2026-08-04.

**Status:** grooming
