# S1 — WebSocket-транспорт воркеров (проектная спецификация)

**Кратко в одну строку:** Унифицировать транспорт ВСЕХ воркеров (on-server + remote) в один постоянный WebSocket, который обслуживается новым асинхронным Python-сервисом **WS-Gateway**, становящимся единственным читателем KeyDB Streams; ни один воркер больше не трогает KeyDB или S3 напрямую, а Symfony остаётся синхронным единственным источником истины для БД + S3 + **терминального** статуса (живой `conv:status` теперь пишет gateway — транзиентный, §5) — что снижает задержку диспетчеризации, не публикуя KeyDB наружу.

- **Статус:** утверждённый дизайн, подсистема только для транспорта.
- **Подсистема:** S1 из трёхчастного редизайна (S1 транспорт → S2 потоковый приём аудио + VAD → S3 приоритеты/маршрутизация/учёт скорости). Этот документ охватывает **только S1**.
- **Дата:** 2026-07-02.

---

## 1. Контекст и цель

**Два старых транспорта, которые S1 сливает в один.**

- **Off-server воркеры** добирались до очереди через HTTP **pull-API** (`App\Controller\Api\WorkerController`, префикс `/api/v1/worker`): `POST /claim`, `GET /jobs/{id}/input`, `POST /jobs/{id}/result`, `POST /jobs/{id}/fail`. Python-воркер (`workers/ai/worker.py`) крутил цикл short-poll: `claim` каждые `poll_interval` (~10 s) → `GET input` → конвертация → `POST result` (multipart) / `POST fail`. Читателем KeyDB Stream (`XREADGROUP`/`XAUTOCLAIM` + `XACK`) со стороны PHP был `WorkerStreamGateway`.
- **On-server воркеры** (document/libreoffice, audio+video/ffmpeg, image, data) читали свой `conv.<type>` Stream **напрямую** из KeyDB и ходили в **S3 напрямую** за входом и за записью результата, каждый сам делая `XACK`.

Поллинг добавлял до `poll_interval` секунд простойной задержки на каждую диспетчеризацию; прямой доступ on-server-воркеров к KeyDB/S3 размазывал владение источником истины и раздавал S3-креды по всем контейнерам.

**Цель S1 — единая модель для ВСЕХ воркеров:**
1. **Все 6 воркеров становятся WS-клиентами** нового gateway; задача проталкивается готовому воркеру в момент попадания в Stream (нет poll-задержки).
2. **WS-Gateway — единственный читатель каждого job-стрима** `conv.ai/document/image/audio/video/data` (владеет `XREADGROUP`/`XACK`/`XAUTOCLAIM`).
3. **Ни один воркер не трогает KeyDB или S3 напрямую** — только gateway (WS) + Symfony API (объёмные payload'ы). S3-креды у воркеров изымаются.

**Жёсткий инвариант — надёжность не меняется.** KeyDB Streams остаются источником истины. WebSocket — это *только* транспорт доставки. Каждая запись по-прежнему является Acked/Pending-записью Stream; ничто в гарантии at-least-once доставки или восстановлении после сбоя не ослабляется. KeyDB **никогда** не публикуется наружу — gateway (в docker-сети `backend`) является единственным компонентом, который с ним общается.

## 2. Не-цели / границы охвата

**В S1:** только транспорт — сервис WS-Gateway, WS-протокол, вынос чтения Stream + ack из PHP в gateway, WS-клиент воркера, унификация пути результата и живого статуса.

**Вне охвата (отложено):**

- **→ S3 (более поздняя подсистема):** приоритеты, маршрутизация с учётом нагрузки, учёт скорости по каждому воркеру, тонко-гранулированные таймауты **на каждую задачу**. S1 использует `XAUTOCLAIM` idle-reclaim с порогом **на каждый `conv.<type>`** (config-map, §6.3); per-task-таймауты и потребление полей состояния воркера (`cpu`/`mem`/`load`/`version`) для маршрутизации — это S3.
- **→ S2:** приём аудио, VAD-нарезка, потоковая конвертация.

**Удалено/выведено в S1** (становится мёртвым кодом, как только появляется WS):

- `POST /api/v1/worker/claim`, Python poll-цикл, gate `PULL_ENABLED` и `POLL_INTERVAL`.
- Прямое чтение `conv.<type>` on-server-воркерами и их прямой доступ к S3 + их self-`XACK`.
- `WorkerStreamGateway::claim()` и `reclaimStale()`/`readNew()` (их половина, читающая Stream) переезжают в gateway.
- **Worker-writable stream `conv.result` и его consumer `QueueResultConsumerCommand`** (§3/§5) — ретайрятся (полная унификация модели результата, Option A).
- **Worker-writable `conv:status`** — воркеры больше не пишут живой статус; его владельцем становится gateway (§5, D5).
- **Публичный `POST /jobs/{id}/fail`** — удаляется; fail идёт через внутренний relay `POST /api/v1/internal/worker/fail` (§7).
- **Внешняя обёртка конверта `{body,headers}`** стокового `redis-messenger` — устраняется кастомным Messenger-транспортом (Option D, §3/§4); стрим несёт чистый single-JSON, декодировка становится одинарной.
- Панель "pull-stats" dev-сервера адаптируется в "WS-stats".

**Честный риск / SPOF:** gateway — это единая точка отказа для **диспетчеризации**: если он недоступен, ни одна новая задача не доставляется. Он **не** является SPOF для **надёжности**: неподтверждённые (unacked) записи выживают в Stream PEL и переотправляются после перезапуска. Один экземпляр gateway приемлем для MVP; HA с несколькими gateway — задача на будущее.

## 3. Архитектура

### Компоненты и зоны ответственности

- **Symfony (backend) — владелец состояния.** Остаётся синхронным. Сохраняет:
  - **Постановку в Stream (диспетч) — БАЙТ-В-БАЙТ БЕЗ ИЗМЕНЕНИЙ.** `ConversionManager::dispatch()`, класс `ConversionMessage`, call-site и `TransportNamesStamp(['conv_'.$key])` routing остаются **байт-идентичными**; ключ маршрутизации — из `ConversionRegistry::streamFor($from,$to,$ocr)`. Меняется НЕ диспетч, а **реализация транспорта** за `conv_*`: см. следующий пункт.
  - **НОВОЕ — кастомный Messenger-транспорт + factory (Option D: чистый single-JSON контракт).** Вместо стокового `redis-messenger` `Connection`, транспорты `conv_*` (`config/packages/messenger.yaml`, `dsn:`/класс транспорта) привязываются к **нашему кастомному транспорту**. Его `add()` делает `XADD` со значением `encode()['body']` **напрямую** в поле стрима `message` — то есть пропускает внешнюю обёртку `{body,headers}`, которую стоковый `Connection::add` безусловно `json_encode`-ит в поле `message`. Итог: поле `message` в стриме = **один чистый JSON** плоского camelCase payload'а задачи (то, что и так возвращает внутренний `Serializer::encode` как `body`), **одна декодировка, а не две**. Формат стрима теперь **наш** (его никто не читает через Messenger — хендлеров нет, `messenger:consume conv_*` закомментирован/запрещён, все чтения — сырой `XREADGROUP`), поэтому продюсер владеет контрактом.
  - `GET /jobs/{id}/input` — стримит вход из S3 (поведение без изменений; как теперь резолвится мета — см. §5). Это **единственный** способ, которым воркер получает вход — прямого доступа к S3 у воркера нет.
  - `POST /jobs/{id}/result` — сохраняет в S3 + БД. Остаётся **только для large-multipart-пути** (§5). **НО больше НЕ делает `XACK`** (ack делает gateway, §4/§5).
  - `POST /api/v1/internal/worker/{result,fail}` — **новые внутренние relay-эндпоинты** (§7): gateway ретранслирует сюда малый inline-результат и fail; Symfony сохраняет (S3 + БД) / помечает failed + возвращает квоту. Публичного `POST /jobs/{id}/fail` больше нет.
  - **Единый терминатор сохранения — `ConversionResultPersister`.** Оба пути (малый через internal relay, большой через `POST /jobs/{id}/result`) сходятся в `App\Service\Queue\ConversionResultPersister`. Стрим `conv.result` и его consumer `QueueResultConsumerCommand` **ретайрятся** — воркеры больше не пишут результат в отдельный Stream (Option A, полная унификация).
  - **Symfony БОЛЬШЕ НЕ читает job-Stream, НЕ читает `conv.result` и БОЛЬШЕ НЕ выполняет XACK.** `PHP MUST NOT run messenger:consume conv_*` — тот же инвариант уже прописан в `messenger.yaml`; теперь он обеспечивается удалением единственного PHP-читателя (путь чтения у `WorkerStreamGateway`) и ретайрментом `QueueResultConsumerCommand`.

- **WS-Gateway (НОВЫЙ асинхронный Python-сервис) — владелец транспортной очереди и живого статуса.** **Единственный** компонент, который читает **все** job-стримы `conv.ai/document/image/audio/video/data` (`XREADGROUP`/`XACK`/`XAUTOCLAIM`) И держит WebSocket-соединения воркеров. Он **не** трогает БД или S3 напрямую — для сохранения он вызывает Symfony по внутреннему HTTP-relay. Он **пишет живой статус `conv:status:{conversionId}`** в KeyDB (§5, D5). Разбор записи стрима — **одна** декодировка `json.loads(message)` (чистый single-JSON контракт, §4).

- **Воркер (Python) — WS-клиент.** Заменяет любой прежний транспорт (poll-цикл off-server / прямое чтение Stream+S3 on-server) постоянным WS-соединением: подключиться → сигнализировать о готовности → получить задачу → скачать вход (через Symfony API) → сконвертировать → вернуть результат. Логика обработки одной задачи (`_process_job` в `worker.py`) переиспользуется дословно; меняется только *транспорт вокруг неё*. Воркер **не держит S3-креды** и **не подключается к KeyDB**.

### Диаграмма потока данных (задача → результат → ack)

```
User upload
   │
   ▼
Symfony ConversionManager::dispatch()  ──XADD──►  KeyDB Stream conv.<type>  (source of truth)
                                                        │
                              (XREADGROUP GROUP convertor <workerId>)
                                                        │
                                                        ▼
                                                   WS-Gateway   (reads EVERY conv.<type>,
                                                   holds WS conns, writes conv:status)
                                                        │  {type:"job", jobId, conversionId, inputKey,...}
                                                        ▼
                                                     Worker (WS client)
                                                        │
                          GET /jobs/{id}/input  ◄───────┤  (worker → Symfony, worker_api token)
                          (S3 input streamed by Symfony)│
                                                        ▼
                                                    convert()  (или fail)
                                              (progress{percent} по WS ~1/s, §4)
                                                        │
   ┌──── small (≤256KB) ─────────┬──────── large ───────────┬──────────── fail ───────────┐
   ▼                             ▼                           ▼                             ▼
worker ──inline(WS)──▶ gateway   worker ──POST /jobs/{id}/   worker ──{type:"result",      worker ──{type:"fail",
                                 result (HTTP multipart,     jobId,resultKey}(WS)──▶ gw     jobId,error}(WS)──▶ gw
                                 firewall worker_api)──▶            │                            │
gateway ──relay HTTP  POST       Symfony persist S3+DB              │                     gateway ──POST /internal/
/api/v1/internal/worker/result             │(payload НЕ идёт        │                     worker/fail (internal
(GATEWAY_INTERNAL_TOKEN)──▶                │ через gateway)         │                     token)──▶ Symfony
Symfony persist (S3+DB)                     │                        │                     (refund квоты)
   │                                       │                        │                            │
   ▼                                       ▼                        ▼                            ▼
gateway XACK conv.<type>          gateway XACK conv.<type>   gateway XACK conv.<type>     gateway XACK conv.<type>
(знает: persist произошёл)        (ack на доверии к WS       (то же large-сообщение)      (после refund)
                                   "result" воркера)
=======================================================================================================
ИНВАРИАНТ: XACK делает ТОЛЬКО gateway и ТОЛЬКО после подтверждённого persist (inline=знает / large,fail=на доверии к WS)
persist ВСЕГДА терминирует в ConversionResultPersister; воркер НИКОГДА не пишет S3/БД/KeyDB напрямую.
```

**Почему relay-блок `gateway → Symfony` есть только в малой (≤256 KB) ветке — и это намеренно, а не баг.** Малая ветка — **единственная**, где полезная нагрузка результата проходит *через* gateway (воркер шлёт `inline` по WS, gateway её и сохраняет через внутренний relay). В большой ветке результат идёт **напрямую** воркер → Symfony (`POST /jobs/{id}/result`, multipart), чтобы крупные payload'ы **не** прокачивались по WS gateway'я и не грузили его память/сокет; поэтому там gateway полезную нагрузку не видит и его роль сводится к одному `XACK`. Это осознанная цена «гибрида по размеру» (§5): маленькое семейство текстовых форматов дешевле переслать inline, чем гонять воркера к Symfony ради нескольких килобайт, а всё крупное — мимо gateway. Инвариант владения ack при этом цел: gateway делает `XACK` **только** после подтверждённого сохранения. На inline-пути «подтверждённое» = gateway сам получил успешный ответ от Symfony (он *знает*, что persist состоялся); на large-/fail-путях gateway делает ack **на доверии** к WS-сообщению воркера `result`/после вызова `/fail`. Обе формы безопасны при at-least-once-доставке + идемпотентности по `conversionId` (§5, §6.3).

## 4. Протокол диспетчеризации (WebSocket)

Основан на кредитах, pull со стороны воркера. Воркер объявляет свою ёмкость; gateway читает одну запись Stream на каждый свободный кредит и проталкивает её. Работу **вытягивают** готовые воркеры → естественная балансировка нагрузки.

### Handshake

При подключении воркер аутентифицируется (§7) и отправляет фрейм **ready**, который также несёт его идентичность, маршрутизацию, версию и снимок состояния:

```json
{ "type": "ready", "workerId": "<stable-id>", "workerType": "<type>", "slots": 1,
  "version": "0.1.6", "cpu": 0.42, "mem": 0.55, "load": 0.30 }
```

- `workerId` — **стабильный** идентификатор на каждый воркер (новое поле конфига, см. §8). Используется дословно как имя consumer'а KeyDB. НЕ должен включать PID (сегодняшний `hostname-pid` в `_poll_loop` нестабилен → запрещён).
- `workerType` — один из `WorkerController::ALLOWED_TYPES` = `ai | document | image | audio | video | data`. **Именно так gateway узнаёт, какой `conv.<type>` Stream читать для этого соединения** (см. §6.2). Маршрутизация закреплена за полем handshake (эквивалентно выразимо как WS-путь `/ws/worker/<type>`; данная спецификация фиксирует форму с **handshake `workerType`**, что соответствует существующему конфигу `WORKER_TYPE` и `ALLOWED_TYPES`).
- **Одно WS-соединение = один `workerType` = один Stream.** Воркер, обслуживающий несколько типов (напр. ffmpeg = `audio` + `video`), открывает **отдельное WS-соединение на каждый тип**, каждое со **своим `workerId`** (напр. `ffmpeg-audio`, `ffmpeg-video`). Это сохраняет инвариант «стабильный consumer + собственный PEL на каждый `conv.<type>`» (§6.1) и не ломает правило §6.2 «одно соединение → один stream».
- `slots` — число параллельных задач, которые воркер готов принять (кредиты). Начинаем с `1`.
- `version` — версия воркера строкой вида `"0.1.6"` (см. «Версия воркера» ниже).
- `cpu`, `mem`, `load` — снимок состояния воркера (доли `0..1` / нормированная нагрузка). См. scope-заметку ниже.

**Версия воркера — откуда берётся значение.** Полная версия компонуется из базовой `APP_VER` (например `0.1`, живёт в `.env`) плюс build-счётчик из **gitignored-файла `.i`** в корне репо (инкрементится на каждой сборке) → `0.1.6`. Полная версия **запекается в образ на этапе сборки**; воркер читает её из своего env/файла и репортит в `ready`. Воркер **не** ходит за версией в KeyDB (чтобы не связывать build-хост с приватным KeyDB). Механика инкремента `.i` — забота CI/Makefile (одна строка-пойнтер, не предмет этой транспортной спецификации): здесь фиксируется только **что** репортится (поле `version`) и **откуда** берётся значение (`.env` `APP_VER` + счётчик `.i`, запечён при build).

**Scope-заметка (жёстко):** в S1 поля `cpu`/`mem`/`load` (в `ready` и `ping`) и `version` **только ПЕРЕНОСЯТСЯ** по проводу — транспорт их доставляет, но НЕ потребляет. Их **потребление** (маршрутизация с учётом нагрузки, учёт скорости по версиям) — это **S3**. Никакой routing-логики здесь не проектируем.

### Форматы сообщений

| Направление | `type` | Поля |
|---|---|---|
| worker → gw | `ready` | `workerId`, `workerType`, `slots`, `version`, `cpu`, `mem`, `load` (handshake, а также переотправляется, чтобы освободить кредит) |
| gw → worker | `ready-ack` | `inlineMax` — авторитетный порог inline-результата (байты до base64); воркер адоптирует это значение вместо своего env `WS_RESULT_INLINE_MAX`. Гарантирует единый порог при раздельном деплое (remote-воркер на своём env). |
| gw → worker | `job` | `jobId`, `conversionId`, `sourceFormat`, `targetFormat`, `inputKey`, `inputBucket` (+ `model`/`subType` МОГУТ ехать вместе для format-логики воркера; воркеры остаются flag-agnostic и используют только форматы) |
| worker → gw | `progress` | `jobId`, `percent`, `stage?` (периодический ~1/s пока задача в работе; см. «Прогресс» ниже) |
| worker → gw | `result` | `jobId`, и **либо** `inline:<data>` (малый) **либо** `resultKey:"<s3key>"` (большой) — см. §5 |
| worker → gw | `fail` | `jobId`, `error` |
| worker → gw | `ping` | `cpu`, `mem`, `load` (периодический; также служит liveness-сигналом для переподключения, §6.6) |
| gw → worker | `pong` | — (ответ на `ping`; отсутствие в течение liveness-окна → воркер переподключается, §6.6) |

В S1 gateway `cpu`/`mem`/`load`/`version` только принимает и логирует/пробрасывает — не потребляет для маршрутизации (см. scope-заметку выше; потребление = S3).

### Прогресс — под-протокол (`progress`)

**Форма:** `{ "type": "progress", "jobId": "<id>", "percent": <0..100>, "stage": "<опц. метка>" }`.

- **Каденс:** воркер шлёт `progress` примерно **раз в секунду** (1s tick) для объёмных/долгих задач, **в дополнение** к `ping` (это разные фреймы: `ping` — liveness+телеметрия, `progress` — прогресс конкретной задачи).
- **Только пока задача в работе.** `progress` эмитится ТОЛЬКО между получением фрейма `job` и терминальным `result`/`fail`. Вне задачи (idle) `progress` не шлётся.
- **Зачем:** несёт живое состояние «processing»/процент, которое при полной унификации модели результата (Option A) иначе было бы потеряно. Gateway на каждый `progress` обновляет живой статус `conv:status:{conversionId}` (§5, D5).
- `percent`/`stage` — best-effort индикатор для UI; `stage` необязателен (напр. `"decoding"`, `"transcoding"`, `"uploading"`). Потерянный/пропущенный `progress`-фрейм не влияет на надёжность (транспорт-индикатор, не источник истины).

### Кредитный цикл gateway (на соединение)

1. По `ready` gateway держит `slots` кредитов.
2. На каждый свободный кредит: `XREADGROUP GROUP convertor <workerId> COUNT 1 BLOCK <ms> STREAMS conv.<workerType> >`.
3. При записи → разобрать конверт, записать мету задачи + выставить `conv:status`=processing (§5), протолкнуть `{type:"job", ...}` воркеру, пометить этот кредит **busy** (запись Stream **pending, не acked**).
4. Воркер шлёт `progress` по ходу (gateway обновляет `conv:status`), по завершении → `result`/`fail` → gateway сохраняет+делает ack (§5) → чистит `conv:status` → освобождает кредит → фактически ещё один `XREADGROUP`. (Воркер МОЖЕТ также переотправить `ready`, чтобы скорректировать `slots`.)

### Разбор записи стрима — ОДНА декодировка (чистый single-JSON контракт, Option D)

Запись Stream в S1 — это **один чистый JSON** плоского camelCase payload'а задачи, лежащий в поле `message` (см. §3, кастомный Messenger-транспорт). **Никакого двойного конверта `{body,headers}`** — внешняя обёртка стокового `redis-messenger` `Connection::add` устранена на стороне продюсера, потому что она **структурна** для стокового Redis-транспорта, и кастомный *serializer* (Option B) её убрать не мог бы; убирает её только кастомный *транспорт* (Option D).

- **Python (`workers/common/envelope.py`):** одна декодировка `json.loads(message)` → dict задачи. Gateway читает стрим напрямую этим декодером.
- **PHP `WorkerStreamGateway::parseMessage()`:** тоже становится **одной** декодировкой (`message` → JSON → задача), а не двумя.
- Сохраняются защиты: poison-message (`parseOrAck`: при ошибке разбора — `XACK`, чтобы сбросить и залогировать, так что искажённая запись не может крутиться вечно) и дроп `conversionId <= 0`.

**Оговорка (не переоценивать выигрыш):** phpredis-footgun `serializer: 0` (`\Redis::SERIALIZER_NONE`) **перенесён, а не устранён** — Redis-writer кастомного транспорта ОБЯЗАН по-прежнему выставлять `SERIALIZER_NONE`, иначе phpredis PHP-сериализует поле `message` и обернёт наш чистый JSON. Это фиксируется как требование к реализации транспорта.

**Контракт стрима теперь НАШ** и заморожен golden-fixture'ом (§9): и PHP-диспетч, и Python-разбор ассертятся против одного зафиксированного чистого single-JSON, так что несовместимость при апгрейде Symfony/phpredis всплывёт громко и в одном изолированном месте, а не тихой рассинхронизацией на проде.

**Файлы (для impl-плана):** новый транспорт+factory под `app-symfony/src/` + `config/packages/messenger.yaml` (`dsn:`/класс); `WorkerStreamGateway::parseMessage` (одна декодировка); `workers/common/envelope.py` (одна декодировка); `docs/queue-contract.md` §2 (описание чистого контракта); golden-fixture `app-symfony/tests/Fixtures/messenger_envelope.golden.json`.

## 5. Result, Ack и живой статус — гибрид по размеру + перенос владения ack + gateway-owned status

**Порог: 256 KB (настраиваемо).** Малые выходы текстового семейства идут inline по WS; большие медиа идут напрямую в Symfony.

- **Малый (≤256 KB: txt/srt/vtt/json):** воркер → `{type:"result", jobId, inline:<data>}` по WS. Gateway ретранслирует inline в Symfony (**внутренний relay-эндпоинт** `POST /api/v1/internal/worker/result`, §7), который сохраняет S3 + БД через `ConversionResultPersister`. Затем gateway делает `XACK`.
- **Большой (audio/video/большие файлы):** воркер сам делает `POST /jobs/{id}/result` в Symfony (multipart, существующий эндпоинт, сохраняет S3 + БД через `ConversionResultPersister`), затем отправляет по WS `{type:"result", jobId, resultKey}`. Затем gateway делает `XACK`.
- **Fail:** воркер → `{type:"fail", jobId, error}`. Gateway вызывает Symfony **внутренний relay** `POST /api/v1/internal/worker/fail` (пометить failed + вернуть квоту), затем делает `XACK`. Публичного `POST /jobs/{id}/fail` больше нет.
- **Expire (CNV-71-03, никем не взятые задачи):** гибридная проверка "воркер существует" (`ConversionManager`) принимает задачу, если для `workerType` есть ХОТЯ БЫ ОДНА строка `worker_capabilities` — даже offline. Если ни один воркер этого типа так и не подключился, запись НИКОГДА не была отдана `XREADGROUP`, поэтому не входит ни в чей PEL и idle-reclaim (§6.3) её структурно не видит. Отдельный фоновый цикл gateway (`workers/gateway/expiry.py`, свой тик `EXPIRY_SWEEP_INTERVAL_S`, по умолчанию 300s) сканирует хвост каждого `conv.<type>` СТРОГО после `last-delivered-id` группы и для записей старше `WORKER_CLAIM_TIMEOUT_MINUTES` (по умолчанию 60 мин) вызывает **внутренний relay** `POST /api/v1/internal/worker/expire` (`{conversionId, reason:"worker_timeout"}`) — та же терминальная запись, что и `fail` (статус + errorMessage + refund + `ConversionFailed`-пропагация по цепочке), но целевой статус `ConversionStatus::Expired`. Идемпотентно тем же terminal-status guard'ом, что и `completed`/`failed` (подробности §5 `queue-contract.md`). `XDEL` записи в стриме — ТОЛЬКО после 2xx-ответа PHP, не раньше.

**Инварианты:**

- Gateway делает `XACK` **только после подтверждённого сохранения**.
- Сохранение ВСЕГДА терминирует в Symfony `ConversionResultPersister` (единственный источник истины). Gateway **никогда** не пишет в БД или S3. Воркер **никогда** не пишет в БД, S3 или KeyDB.
- Порог 256 KB — это значение конфига gateway/воркера.

### Владение метой задачи (закрывает неявный пробел)

Сегодня `GET /jobs/{id}/input` и `POST /jobs/{id}/result` резолвят мету задачи (`inputBucket`, `inputKey`, `conversionId`, `stream`, `targetFormat`) из Redis-ключа `worker:job:{jobId}` (TTL 24 h), который пишется PHP `WorkerStreamGateway::claim()`. Как только gateway становится владельцем чтения Stream, **PHP перестаёт писать этот ключ**, поэтому те эндпоинты сломались бы.

**Закрепление:** **WS-Gateway пишет `worker:job:{jobId}` при диспетчеризации** — идентичный ключ, идентичный контракт полей, TTL 24 h — в момент, когда он проталкивает фрейм `job`. Эндпоинты Symfony `input()`/`result()` затем читают его точно как раньше, без изменений. При ack gateway делает `DEL` этого ключа (зеркалит `WorkerStreamGateway::ack()`).

> **Два РАЗНЫХ ключа, не путать:** `worker:job:{jobId}` — мета задачи для эндпоинтов input/result (выше). `conv:status:{conversionId}` — живой статус конвертации (ниже, D5). Оба чистятся при ack, но это разные ключи с разным жизненным циклом и разным пространством id (`jobId` vs `conversionId`).

### Живой статус конвертации `conv:status` — владелец gateway (D5)

**Полная унификация (Option A) ретайрит worker-writable `conv.result` и worker-writable `conv:status`.** Чтобы живое состояние «processing»/прогресс не потерялось, его владельцем становится **gateway** (единственный компонент с доступом к KeyDB):

- **При диспетчеризации** (проталкивание `job`): gateway делает `HSET conv:status:{conversionId} state=processing` (TTL 24 h).
- **На каждый `progress`-фрейм** (§4): gateway обновляет `HSET conv:status:{conversionId} state=processing percent=<n> stage=<...>`.
- **При терминале/ack** (`result`/`fail` сохранены и записаны в БД): gateway **чистит** хеш (`DEL conv:status:{conversionId}`) — дальше истина живёт в терминальной строке БД.

**`App\Service\Queue\ConversionStatusReader` и `ConversionManager::getStatus()` — БЕЗ ИЗМЕНЕНИЙ.** Они по-прежнему читают `conv:status:{conversionId}` (`hGetAll`), а при очищенном/протухшем хеше падают обратно на терминальную строку MariaDB (`getStatus()` уже так устроен). То есть `conv:status` продолжает существовать и работать как раньше для читателя — меняется только **писатель**: теперь это **gateway**, а не воркер. Воркеры KeyDB не трогают. Поля `percent`/`stage` — дополнительные в хеше (для будущего UI-прогресса); `getStatus()` в S1 их не сюрфейсит (остаётся как есть) — их потребление в DTO — более поздняя работа.

### Смена владения ack — ЗАЯВИТЬ ГРОМКО

**Изменение поведения:** `WorkerController::result()` и `fail()` каждый сейчас вызывают `$this->gateway->ack($meta['stream'], $jobId)`. **S1 удаляет оба вызова** (`fail()` вообще удаляется как публичный эндпоинт). `XACK` полностью переезжает в gateway. **Никто не имеет права заново добавлять `XACK` в Symfony** — Symfony больше не знает отношения Stream/consumer и не должен трогать PEL.

**Асимметрия ack (обе безопасны):**
- **Inline-путь** — gateway делает ack, потому что *он сам сделал вызов сохранения* (internal relay) и увидел успешный ответ. Он *знает*, что сохранение произошло.
- **Large-путь** — gateway делает ack **на доверии** к WS-сообщению воркера `{type:"result", resultKey}`, утверждающему «я запостил результат». Gateway не наблюдал сам POST.

Оба варианта безопасны при **at-least-once + идемпотентности по `conversionId`** (§6.3): потерянная/дублированная доставка просто перезаписывает тот же детерминированный ключ результата `results/{Y}/{m-d}/{id}.{ext}` (`WorkerController::buildResultKey()`). Худший случай лгущего/сбойного воркера на large-пути: запись acked, но результат не сохранён → конвертация остаётся незавершённой, а вход авто-протухает; приемлемо для MVP и детектируется по статусу. (Ужесточение этого — например, gateway проверяет сохранение перед ack'ом больших результатов — отложено до S3.)

## 6. Надёжность / отказы

### 6.1 Именование consumer-группы (СТАБИЛЬНОЕ, на каждый воркер)

- Группа остаётся `convertor` (`WorkerStreamGateway::GROUP`).
- **НЕ использовать имена consumer'ов на каждое соединение / эфемерные.** KeyDB никогда сам не удаляет consumer'ов, так что свежее имя на каждое переподключение течёт (leak) consumer'ами и оставляет застрявшие PEL-записи под мёртвыми именами.
- **Использовать СТАБИЛЬНОЕ имя consumer'а на каждый воркер = handshake `workerId`.** Новое поле конфига воркера (§8), без PID-компонента. Переподключающийся воркер переиспользует то же имя, так что его собственные in-flight (pending) записи остаются атрибутируемыми и восстановимыми. Мульти-тип воркер (ffmpeg) даёт по одному `workerId` на тип (§4).
- **Consumer на каждый воркер, НЕ один глобальный consumer gateway.** Gateway выдаёт `XREADGROUP`/`XACK` под `workerId` каждого подключённого воркера. Это суть: PEL на каждый воркер — вот что делает восстановление-при-переподключении и `XAUTOCLAIM` атрибутируемыми правильному воркеру.
- **При переподключении** gateway сначала восстанавливает in-flight записи этого воркера: `XREADGROUP GROUP convertor <workerId> COUNT <n> STREAMS conv.<type> 0` (id `0` возвращает уже-pending записи для этого consumer'а), переотправляет их, затем возобновляет чтение новых записей с `>`.

### 6.2 Маршрутизация worker→stream (несущая нагрузку)

Gateway отображает соединение на его Stream через handshake `workerType`: он читает **`conv.<workerType>`**. `workerType` валидируется против `ALLOWED_TYPES` (`ai|document|image|audio|video|data`); неизвестный тип → reject/close (§7). **Одно соединение потребляет ровно один stream своего типа**; воркер, обслуживающий несколько типов (ffmpeg = audio+video), открывает по соединению на тип (§4). Это ровно текущая модель `WORKER_TYPE`, только протолкнутая по WS вместо отправки в теле `POST /claim`.

### 6.3 Reclaim → re-dispatch (сделать явным; порог — ПО КАЖДОМУ типу)

- **Кто:** **gateway** крутит периодический reclaim-цикл (фоновая async-задача внутри процесса gateway).
- **Триггер — ТОЛЬКО idle-timeout.** Единственное условие reclaim — запись провисела в PEL дольше idle-порога СВОЕГО типа. **НИКАКОГО reclaim по событию WS-дисконнекта** (см. запрет-ловушку ниже).
- **Idle-порог — на каждый `conv.<type>` (config-map, не единое значение).** Разные типы конвертации имеют разное максимальное время обработки, поэтому единый порог непригоден.
- **Принцип подбора (жёстко):** idle-порог типа ДОЛЖЕН превышать максимальное ожидаемое время обработки задачи этого типа. Иначе медленная-но-живая задача будет переклеймлена и обработана дважды (video — долго, image — коротко; отсюда и разброс).
- **Черновые значения** (пометка: **черновые, регулируются позже**):

  | Stream | idle-порог (черновой) |
  |---|---|
  | `conv.document` | ~300s |
  | `conv.image` | ~120s |
  | `conv.audio` | ~300s |
  | `conv.video` | ~600s |
  | `conv.data` | ~180s |
  | `conv.ai` | ~300s |

  Очень короткие CHUNK-значения для потокового аудио — это **S2** (будут добавлены там, не сейчас).
- **Частота:** reclaim-цикл работает с фиксированным интервалом (например, каждые ~60 s; настраивается). На каждый тип он вызывает `XAUTOCLAIM conv.<type> convertor <reclaimConsumer> <minIdle[type]> 0-0 COUNT <n>`, чтобы вытянуть записи, простаивающие дольше порога *этого типа* (т.е. от воркеров, которые по-настоящему умерли посреди задачи, или от gateway, который перезапустился).
- **Критично — переклеймленная запись заново входит в ТОТ ЖЕ путь диспетчеризации.** Переклеймленная запись **НЕ** паркуется в PEL reclaimer'а. Gateway немедленно трактует её как свежепрочитанную запись: разобрать конверт → (пере)записать `worker:job:{jobId}` + `conv:status`=processing → передать в логику кредитов/диспетчеризации → протолкнуть фрейм `job` следующему **готовому** воркеру под `workerId` *того* воркера (который становится новым владеющим consumer'ом). Reclaim-цикл — это только *триггер*; доставка идёт через единственный путь «диспетчеризация готовому воркеру».

> **Ловушка, запрещённая явно:** НЕ добавлять «немедленный reclaim по WS-дисконнекту». Он сталкивается со стабильными именами consumer'ов (§6.1): transient-дисконнект — норма, воркер переподключается под тем же `workerId` и возобновляет свой PEL (§6.6); reclaim по дисконнекту переклеймил бы ещё-живую задачу и вызвал двойную диспетчеризацию. Триггер reclaim остаётся **только idle-timeout**. Ordering, который делает это корректным: **окно переподключения/liveness ≪ per-type idle-порог** (секунды против 120–600 s) — быстрый reconnect (§6.6, путь «a») успевает раньше, чем сработает reclaim-backstop.

### 6.4 Сценарии отказа

- **Transient-дисконнект воркера (WS отвалился, воркер жив)** → воркер быстро переподключается под тем же `workerId` → `XREADGROUP ... 0` возобновляет его собственный PEL (§6.6, путь «a») → **reclaim НЕ срабатывает**, дубликата нет.
- **Воркер по-настоящему умер (не переподключается)** → запись так и не acked → остаётся pending → по достижении per-type idle-порога (§6.3) `XAUTOCLAIM` переотправляет через путь reclaim→re-dispatch (backstop, §6.6, путь «b»).
- **Перезапуск gateway** → все pending-записи выживают в Stream PEL; после перезапуска reclaim-цикл (и восстановление при переподключении на каждый воркер) переотправляют их. Живой `conv:status` при рестарте может протухнуть/очиститься — читатель падает на строку БД (§5). Надёжность цела.
- **At-least-once ⇒ возможна дублирующая доставка ⇒ конвертация ДОЛЖНА быть идемпотентной по `conversionId`** (уже так: детерминированный ключ результата перезаписывается). **Зафиксировано как жёсткое требование.**
- **Auth-fail / искажённый фрейм / слишком большой фрейм** → закрыть с WS-кодом **1008** (policy violation) / reject (§7).

### 6.5 SPOF

Повторено из §2: диспетчерский SPOF, не SPOF надёжности. Один экземпляр OK для MVP; HA — на будущее.

### 6.6 Переподключение воркера + модель liveness (одна связная модель)

Три фичи — **стабильное имя consumer'а** (§6.1), **idle-reclaim** (§6.3) и **ping/pong** (§4) — должны складываться в ОДНУ непротиворечивую модель, а не три пересекающиеся. Здесь она описана целиком; §6.1/§6.3/§6.4 — её грани.

**Две РАЗНЫЕ шкалы liveness (не смешивать):**
- **Сторона воркера (быстрая, секунды):** воркер шлёт `ping` периодически; если `pong` не пришёл в течение liveness-окна (по критерию «N пропущенных ping'ов»), **воркер сам переподключается** под тем же `workerId`. То же переподключение он делает и когда WS просто оборвался. По факту переподключения **gateway** (единственный читатель KeyDB) возобновляет PEL этого `workerId`: `XREADGROUP GROUP convertor <workerId> ... STREAMS conv.<type> 0` (id `0` возвращает уже-pending записи ЭТОГО consumer'а) → переотправляет их воркеру. **Экспоненциальный backoff** на стороне воркера, чтобы не устроить reconnect-шторм.
- **Сторона gateway (медленная, минуты):** per-type idle-timeout → `XAUTOCLAIM` → re-dispatch (§6.3). Это **backstop только для по-настоящему мёртвого** воркера.

**Ordering, который делает модель корректной:** liveness/reconnect-окно (секунды) **≪** per-type idle-порог reclaim'а (120–600 s, §6.3). Именно поэтому быстрый reconnect успевает раньше, чем сработает backstop. Тюнить пороги, сохраняя это неравенство.

**Модель поведения (две ветки, никаких противоречий):**
- **(a) Transient-обрыв** → быстрый reconnect (тот же `workerId`) → возобновление своего PEL → **reclaim НЕ срабатывает, дубликата нет**.
- **(b) Мёртвый воркер** (не переподключается никогда) → per-type idle-timeout → `XAUTOCLAIM` → re-dispatch другому **готовому** воркеру. Backstop.

Быстрый reconnect существует ровно затем, чтобы попасть в ветку (a) до того, как выстрелит backstop (b). Если обе всё же наложатся (reconnect и reclaim пересеклись) — покрывается идемпотентностью по `conversionId` (§6.3): худшее — та же задача доедет дважды и перезапишет тот же детерминированный ключ результата.

**Liveness-таймаут КОНФИГУРИРУЕМ.** Флаг: единое жёсткое окно ~2 s может быть слишком тесным для удалённого AI-воркера над WAN (скачок латентности → ложный reconnect); поэтому предпочитаем критерий **«N пропущенных ping'ов»**, а не единичный дедлайн. Значения — черновые, «потом отрегулируем»; в S1 задаём как tunable с грубым дефолтом.

**Опциональная приятность (не обязательна к реализации в S1):** graceful-сообщение **`draining`** позволяет чисто-останавливающемуся воркеру немедленно освободить свой PEL (безопасно — он обещает не возобновлять эти записи), не дожидаясь idle-порога.

## 7. Аутентификация и сеть

### Три границы аутентификации

**(a) Worker → Gateway (WS handshake):** bearer-токен = **тот же `WORKER_API_TOKEN`**, отправляется в WS upgrade-запросе (заголовок `Authorization: Bearer …`, или subprotocol/`?token=`, если WS-библиотека вынуждает — заголовок предпочтителен). Gateway отклоняет отсутствующий/невалидный токен, закрывая `1008` до того, как обработан хоть какой-то `ready`.

**(b) Worker → Symfony (прямой HTTP):** для `GET /jobs/{id}/input` и **large-путя** `POST /jobs/{id}/result` воркер вызывает Symfony напрямую, используя `WORKER_API_TOKEN` на существующем файрволе `worker_api` — без изменений от сегодняшнего.

**(c) Gateway → Symfony (internal relay):** для малых inline-результатов, для `fail` и для `expire` (CNV-71-03, никем не взятые задачи — §5) gateway вызывает Symfony для сохранения. **Отдельные внутренние relay-эндпоинты** `POST /api/v1/internal/worker/result`, `POST /api/v1/internal/worker/fail`, `POST /api/v1/internal/worker/dlq-fail` и `POST /api/v1/internal/worker/expire` на **собственном файрволе**, аутентифицированном **отдельным внутренним токеном gateway** (`GATEWAY_INTERNAL_TOKEN`).

**Обоснование:** `POST /jobs/{id}/result` всё равно меняется (он теряет свой `XACK`, §5). Вызывающий inline-relay (gateway, JSON-тело) — иной принципал, чем воркер (multipart, токен `worker_api`); отдельный эндпоинт + токен для persistence-relay не даёт публичному токену `worker_api` подрабатывать backend-to-backend credential'ом для сохранения и позволяет им эволюционировать независимо. (Двойной токен на одном маршруте `/result` рассматривался и отклонён: он перегружает один эндпоинт двумя формами тела и двумя принципалами.) Публичный `POST /jobs/{id}/fail` **удаляется** — fail идёт только через internal relay. Large-путь multipart `POST /jobs/{id}/result` остаётся на файрволе `worker_api` для воркера. `dlq-fail` (DLQ-consumer, отдельная более поздняя задача) и `expire` (CNV-71-03, §5) добавились позже на ТОМ ЖЕ файрволе/токене — они разделяют принцип S1 (backend-to-backend, gateway-инициированный вызов), не только исходную пару `/result`/`/fail`; этот раздел документа изначально их не перечислял.

### Сеть

- **KeyDB остаётся приватным.** Он достижим только внутри docker-сети `backend`; он **никогда** не публикуется наружу. Gateway (на `backend`) — единственный клиент KeyDB для Streams.
- **Gateway подключён к сетям `backend` (достучаться до keydb) + `default` (публичный фронт `nginx` + egress к Symfony).** НЕ к `common`.
- **WS экспонируется наружу через локальный сервис `nginx` репо** (публичный фронт на `default`): терминация TLS + заголовки `Upgrade`/`Connection` для WS-handshake, новый `location /ws/worker/`, проксирование в контейнер gateway. Удалённый воркер (например, AI на домашнем WSL+GPU) подключается к публичному WS URL (`wss://…/ws/worker/`).
- HTTP-эндпоинты воркера в Symfony остаются достижимы для воркера через существующий публичный URL приложения (`API_BASE_URL`), через тот же `nginx`.

## 8. Развёртывание

- **Новый контейнер: WS-Gateway.** Python async (например, `websockets`/`aiohttp` + `redis-py`), в сетях `backend` + `default`. Образ публикуется в наш **Harbor**-registry (проект `convertor`).
- **Воркеры после миграции** — WS-клиенты: они **уходят с сети `backend`** (KeyDB им больше не нужен) и **лишаются S3-кред** (остаются на `default` для доступа к `nginx`/Symfony API). Прямой доступ к KeyDB/S3 у воркеров изымается — это часть D2-унификации.
- **Все операции docker compose — только через Makefile-таргеты** — добавить таргеты build/up/down/logs для gateway; не вызывать `docker compose` напрямую. `make docker-check` (= `docker compose config -q`) должен проходить с подключённым новым сервисом.
- **Удалённый воркер** пуллит свой образ из Harbor на своём хосте и подключается по WS к публичному `wss://…/ws/worker/` URL.

### Переменные окружения (секреты ПУСТЫЕ в трекаемых файлах)

Трекаемые `.env` / `.env.local_example` держат **пустые плейсхолдеры**; реальные значения только в `.env.local` (gitignored). Новые/изменённые переменные:

| Переменная | Где | Примечания |
|---|---|---|
| `GATEWAY_INTERNAL_TOKEN` | трекаемый `.env` = **пусто**; реальное в `.env.local` | НОВАЯ. Аутентификация внутреннего relay Gateway→Symfony (граница c, оба эндпоинта `result`/`fail`). |
| `WORKER_API_TOKEN` | уже пусто в трекаемом `.env` | Переиспользуется для worker→gateway WS (граница a) + worker→Symfony напрямую (граница b). |
| `WORKER_ID` | конфиг воркера (новое поле) | НОВАЯ. **Стабильное** имя consumer'а; без PID. Заменяет `hostname-pid`. Уникально на экземпляр; мульти-тип воркер — по id на тип. |
| `GATEWAY_WS_URL` | конфиг воркера | НОВАЯ. `wss://…/ws/worker/` публичный WS-эндпоинт. |
| `WS_RESULT_INLINE_MAX` | конфиг gateway/воркера | Порог inline в байтах, по умолчанию `262144` (256 KB). Gateway публикует своё значение воркеру в `ready-ack.inlineMax`; воркер адоптирует его. Собственный `WS_RESULT_INLINE_MAX` воркера — дефолт до получения `ready-ack`. |
| `RECLAIM_IDLE_MS_<TYPE>` | конфиг gateway (config-map по типам) | НОВАЯ. Idle-порог reclaim **на каждый `conv.<type>`** (§6.3), не единое значение. Черновые дефолты: document `300000`, image `120000`, audio `300000`, video `600000`, data `180000`, ai `300000`. Регулируются позже. |
| `RECLAIM_INTERVAL_S` | конфиг gateway | НОВАЯ. Частота reclaim-цикла, по умолчанию `60`. |
| `WS_BLOCK_MS` | конфиг gateway | НОВАЯ. `XREADGROUP BLOCK` в ms. |
| `APP_VER` | трекаемый `.env` | НОВАЯ. Базовая версия воркера (например `0.1`). Компонуется со счётчиком `.i` → полная `version` (например `0.1.6`), запекается в образ при build (§4). |
| `WS_PING_INTERVAL_S` | конфиг воркера | НОВАЯ. Период отправки `ping` воркером (§4/§6.6). Черновой дефолт, tunable. |
| `WS_PROGRESS_INTERVAL_S` | конфиг воркера | НОВАЯ. Каденс `progress`-фреймов (§4), по умолчанию `1` (1s tick). Эмитится только пока задача в работе. |
| `WS_LIVENESS_MISSED_PINGS` | конфиг воркера | НОВАЯ. Порог «N пропущенных ping'ов» без `pong` → переподключение (§6.6). Предпочтён единичному дедлайну (WAN-скачки). Черновой дефолт, tunable. |
| `WS_RECONNECT_BACKOFF_*` | конфиг воркера | НОВАЯ. Параметры экспоненциального backoff переподключения (§6.6), чтобы не устроить reconnect-шторм. |
| **Удалено** | — | `POLL_INTERVAL`, `PULL_ENABLED` (воркер), `RECLAIM_MIN_IDLE_MS` (единое значение заменено per-type map), S3-креды у on-server-воркеров и любой код, ссылающийся на `POST /claim` или на прямое чтение `conv.<type>`/`conv.result`. |

> `.i` — gitignored-файл-счётчик сборок в корне репо; инкремент — забота CI/Makefile (одна строка, §4), не переменная окружения. В образ запекается уже скомпонованная полная `version`.

Прокладка конфига следует существующему паттерну: все чтения `os.getenv` централизованы в `workers/ai/config.py` `load_config()`; конвенция «пусто в трекаемом / реальное в `.env.local`» уже используется для `WORKER_API_TOKEN` и `REDIS_PASSWORD`.

## 9. План тестирования

**Golden-sample контракт-тест (страж НАШЕГО чистого single-JSON контракта, §3/§4):**
- Fixture `app-symfony/tests/Fixtures/messenger_envelope.golden.json` держит **чистый single-JSON** ровно в той форме, которую пишет кастомный транспорт (плоский camelCase payload задачи), — **не** двойно-обёрнутую форму.
- **PHP-сторона:** диспетч через `ConversionManager::dispatch()` (байт-идентичный, §3) → тест ассертит, что **байты поля `message` записи Stream == fixture** (т.е. кастомный транспорт XADD-ит именно чистый JSON, без внешней обёртки `{body,headers}`, с `SERIALIZER_NONE`).
- **Python-сторона:** `parse(fixture)` (`workers/common/envelope.py`, одна `json.loads`) == ожидаемый dict задачи.
- Так контракт стрима, которым мы теперь **владеем**, заморожен с обеих сторон: любой дрейф (апгрейд Symfony/phpredis, случайное возвращение обёртки или PHP-сериализации) даёт **громкий отказ в одном изолированном месте**, а не тихую рассинхронизацию на проде. poison-запись → acked+дропнута (`parseOrAck`).

**Gateway unit (mock KeyDB + фейковый WS-воркер):**
- кредит → `XREADGROUP` → протолкнуть `job` → по `result` → вызов сохранения (internal relay) → `XACK` (проверить, что ack происходит только после того, как persist-мок вернул success).
- reclaim по **idle-timeout** (а НЕ по дисконнекту): засеять pending-запись, прокрутить idle за per-type-порог (§6.3), проверить, что reclaim-цикл передиспетчеризует её через обычный путь проталкивания `job` (не оставлена запаркованной). Ассертить, что **триггер — именно пересечение idle-порога**, а не событие обрыва WS.
- transient-reconnect без reclaim: воркер с pending-записью роняет WS и быстро переподключается под тем же `workerId` до истечения idle-порога → `XREADGROUP ... 0` возобновляет его PEL, reclaim **не** срабатывает, дубликата нет (§6.6, путь «a»).
- маршрутизация результата: inline (≤256 KB) против large (`resultKey`) против `fail` → правильная ветка (internal relay `result` / trust-ack / internal relay `fail` refund).
- `progress`-фрейм: воркер шлёт `progress{percent,stage}` пока задача в работе → gateway обновляет `conv:status`; проверить, что вне задачи `progress` не эмитится.
- `conv:status` write-lifecycle (D5): dispatch → `HSET state=processing`; на `progress` → обновление `percent`/`stage`; на терминале/ack → `DEL`. Ассертить, что `ConversionStatusReader.read()` видит эти значения и что после ack читатель падает на строку БД.
- `ping`/`pong` liveness: воркер шлёт `ping`, gateway отвечает `pong`; при N пропущенных `pong` воркер инициирует reconnect (§6.6).

**Интеграция:**
- Фейковый воркер подключается, `ready` (с `version`/`cpu`/`mem`/`load`), засеянная запись `conv.<type>` проталкивается, воркер возвращает результат, запись `XACK`нута (проверить, что PEL пуст).
- По-настоящему мёртвый воркер посреди задачи → per-type idle-timeout → reclaim → переотправка второму фейковому воркеру (backstop, §6.6 путь «b»).
- Маршрутизация Stream: воркер с `workerType:"image"` всегда получает только записи `conv.image`.
- **Миграция всех воркеров:** прогнать по одному фейковому WS-клиенту на каждый тип (`ai/document/image/audio/video/data`), убедиться, что каждый читается gateway'ем из своего `conv.<type>`, что ни один клиент не открывает соединение к KeyDB/S3, и что мульти-тип воркер (audio+video) держит два отдельных `workerId`-соединения с непересекающимися PEL.

**Идемпотентность:**
- Форсировать дублирующую доставку (тот же `jobId`/`conversionId`) → ровно один сохранённый результат по детерминированному ключу; без двойного списания/возврата квоты.

## 10. Открытые риски

- **Диспетчерский SPOF** (один gateway). Митигация отложена до HA с несколькими gateway (на будущее). Не риск для надёжности.
- **Trust-ack на large-пути** — gateway делает ack до наблюдения сохранения. Ограничено идемпотентностью; ужесточение отложено до S3.
- **Таймауты WS в `nginx`** — WS read-timeout на `location /ws/worker/` ДОЛЖЕН превышать самую долгую конвертацию (video ~600 s), а интервал `ping`-keepalive воркера ДОЛЖЕН оставаться ниже этого таймаута; иначе долгая задача разорвёт WS. Валидировать под конфигом локального `nginx`.
- **Дисциплина уникальности `workerId`** — два воркера, разделяющие один `workerId`, разделяли бы один PEL и могли бы двойно-потреблять/путать восстановление; операционное (deploy-docs) требование, чтобы `WORKER_ID` был уникален для каждого экземпляра воркера (для мульти-тип воркера — уникален на тип).
- **Подбор per-type idle-порогов** (§6.3) — черновые значения; порог типа обязан превышать макс. время обработки задачи этого типа, иначе медленная-но-живая задача переклеймится и обработается дважды. Регулируется по факту наблюдаемых длительностей.
- **Ordering liveness ≪ idle-порог** (§6.6) — при тюнинге сохранять неравенство «окно reconnect (секунды) ≪ per-type idle-порог (минуты)»; иначе backstop-reclaim может выстрелить раньше быстрого reconnect и вызвать лишнюю передиспетчеризацию (покрыто идемпотентностью, но нежелательно).
- **Liveness-окно над WAN** (§6.6) — единичный жёсткий дедлайн ~2 s тесен для удалённого AI-воркера; критерий «N пропущенных ping'ов» — tunable, «потом отрегулируем».
- **Адаптация dev-сервера** — минимальная "WS-stats" (состояние соединения + in-flight + последний pong) вместо "pull-stats"; убедиться, что harness dev-сервера всё ещё прогоняет реальный end-to-end путь по WS.
