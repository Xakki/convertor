# Контракт настроек конвертации

Этот документ фиксирует публичный контракт настроек, стабилизированный CNV-85 и
CNV-92. Runtime-источники контракта — `config/catalog/conversion_settings.json`,
`ConversionSettingsCatalog`, `SettingsField` и `ConversionOptionsValidator`.
Каталог форматов (`conversion_pairs.json`) остаётся отдельным артефактом: профили
настроек накладываются на его пары правилами `assignments`.

## Границы контракта

Настройки доступны через `GET /api/v1/formats` и передаются при `POST /convert`
как поля `options[<key>]` (PHP form encoding собирает их в `options.<key>`).
Клиент сначала получает каталог, но сервер всё равно заново разрешает профиль и
валидирует каждое значение. Нельзя передавать аргументы командной строки или
сырые параметры FFmpeg, LibreOffice, Pillow и другого worker-а: публичная
грамматика ограничена шестью типами полей ниже.

`options` — это только настройки конкретной конвертации. Поля `from`, `to`,
`ocr`, файл/текст и прочие параметры запроса не являются полями профиля.

## Ответ `GET /api/v1/formats`

Ответ содержит две части:

```json
{
  "formats": [
    {
      "from": "jpg",
      "to": "png",
      "category": "image",
      "isAi": false,
      "ocrCapable": false,
      "settingsProfile": "image.raster"
    }
  ],
  "settings": {
    "version": "2026-08-26.1",
    "profiles": {
      "image.raster": {
        "id": "image.raster",
        "label": "Изображение",
        "fields": []
      }
    }
  }
}
```

Пример показывает форму ответа, а не полный список живых пар и профилей.

- `formats[].settingsProfile` — идентификатор записи в
  `settings.profiles`. `null` означает, что у пары нет настраиваемых полей;
  это явное значение, а не пропущенный ответ.
- Профиль сериализуется один раз и может использоваться несколькими парами.
  В ответ попадают только профили, на которые ссылается хотя бы одна
  опубликованная пара.
- `settings.version` — непрозрачная непустая строка версии каталога. Клиент
  использует её для отделения сохранённых значений старой схемы от текущих.
  При несовместимом изменении профиля версию нужно поднять.
- Профили в ответе персонализированы под вызывающего: `editable` вычисляется
  для каждого поля и каждого варианта `select`.
- Профиль `api.chat` публикуется только если есть единый live-набор
  валидированных моделей API. Его `model` — динамический `select`: варианты и
  `default` приходят из этого live-набора, а не из статического JSON.

### Профиль и поле

Профиль имеет непустые `id`, `label` и список `fields`. Идентификатор профиля —
строка в нижнем регистре с точками, например `image.raster`.

Каждое поле имеет следующие обязательные значения:

| Поле | Значение |
|---|---|
| `key` | Уникальный ключ в профиле; начинается со строчной буквы и содержит буквы, цифры и `_`. |
| `type` | Один из `range`, `select`, `number`, `text`, `boolean`, `color`. |
| `label` | Непустая отображаемая подпись. |
| `minPlan` | Обязательный уровень доступа: `guest`, `free`, `basic` или `pro`. Выбирается по стоимости поля, без неявного значения. |
| `ai` | Boolean; AI-поля в текущем контракте не редактируются ни одним уровнем. По умолчанию `false`. |
| `default` | Необязательное значение. `null` означает отсутствие значения по умолчанию. |

Специализированные ключи:

- `range` и `number` требуют целые `min` и `max`, где `min <= max`; `step`
  положителен и по умолчанию равен `1`; `unit` необязателен. `range` и `number`
  одинаково валидируются сервером, различие — только представление в UI.
- `select` требует непустой список `options`. Каждый вариант имеет непустые
  `value`, `label` (по умолчанию равен `value`) и обязательный `minPlan`.
  Уровень варианта не может быть ниже уровня поля.
- `text` требует положительный `maxLength`; `minLength` необязателен и по
  умолчанию равен `0`; `pattern` необязателен и применяется как полное
  Unicode-сопоставление строки.
- `boolean` принимает boolean, integer `0`/`1` или строки `1`, `0`, `true`,
  `false`, `yes`, `no`, `on`, `off` (без учёта регистра).
- `color` — строка строго вида `#RRGGBB`; результат нормализации — верхний
  регистр.
- `dynamic: true` разрешён только для `select`. У dynamic-select нет статичных
  `options` и `default`: оба значения должны прийти из проверенной live
  capability.

Неизвестные ключи в JSON каталога, профиле, поле или варианте `select` — ошибка
загрузки. Профиль с пустыми полями, повторным `key` или невалидным `default` не
может быть опубликован.

## Доступ, OCR и редактируемость

Уровни образуют лестницу `guest < free < basic < pro`. Для авторизованного
пользователя имя плана нормализуется; неизвестное имя безопасно сводится к
минимальному авторизованному уровню `free`. Гость получает уровень `guest`.

Поле редактируемо, когда уровень вызывающего не ниже его `minPlan` и поле не
помечено `ai`. Для `select` дополнительно проверяется `minPlan` выбранного
варианта. Один и тот же предикат используется для `editable` в `/formats` и для
приёма `POST /convert`.

Ось OCR отдельна от plan-доступа:

- `ocrCapable` описывает возможность пары, но профиль в `/formats` разрешается
  для маршрута `ocr=false`.
- При включённом OCR клиент скрывает настройки и отправляет пустой набор
  `options`. Сервер не принимает настройки для OCR-маршрута и возвращает
  `422` с кодом `settings_not_supported`, если они присланы.
- Клиентский renderer CNV-92 fail-closed: malformed `/formats` payload сбрасывает
  профили, а не пытается угадать структуру. Поля и варианты с `editable !== true`
  не должны редактироваться или попадать в отправку.

## Сохранение состояния в браузере

CNV-92 сохраняет локальные значения по ключу целевого формата и включает версию
каталога: `convertor:settings:<to>`. Сохранённые значения применяются только
при совпадении `settings.version`, если значения являются plain record и
совместимы с текущими полями. Повреждённое или недоступное `localStorage`
безопасно игнорируется.

Перед отправкой renderer строит новый нормализованный набор только из текущих
редактируемых полей. При OCR результат всегда `{}`. Значения недоступных
вариантов `select`, неизвестные ключи и несовместимые сохранённые значения не
отправляются.

## Нормализация и ошибки `POST /convert`

`ConversionOptionsValidator` не копирует входной массив. Он обходит поля
разрешённого профиля, применяет defaults и записывает только whitelisted
значения в каноническом виде:

1. Нет профиля и `options` пуст — запрос продолжается с `options: []`.
2. Нет профиля и присланы настройки — `422`, `settings_not_supported`.
3. Поле не существует — `422`, `unknown_option`.
4. Поле или его значение недоступно по плану — `422`,
   `option_plan_required`.
5. Неверный тип — `422`, `invalid_option_type`.
6. Нарушены `min`/`max`/`step` — `422`, `option_out_of_range`.
7. Значение не прошло enum, pattern или формат цвета — `422`,
   `invalid_option_value`.

Целое принимается как integer или как строка целого из multipart/form-data;
дроби, boolean, пустая строка и формы с ведущим нулём отклоняются. Нормализованный
результат сохраняет integer/boolean/string, а не исходное строковое представление
формы.

Поле с непустым `default` материализуется в результат даже если клиент его не
прислал и даже если текущий уровень не может его редактировать. Поле без
`default` остаётся отсутствующим. Для dynamic `api.chat.model` отсутствие
значения заполняется текущим live-default; выбранная модель должна входить в
текущий общий список моделей.

## Версионирование и изменение каталога

`conversion_settings.json` правится вручную и коммитится; он не является
результатом `make formats-catalog` и не изменяет `conversion_pairs.json`.
Загрузчик читает только известные ключи и падает громко при битом JSON, неверной
схеме или неизвестной ссылке assignment.

При добавлении или несовместимом изменении профиля:

1. Добавить профиль с dot-separated id и непустым списком полей.
2. Добавить правила в `assignments`; они проверяются сверху вниз, первое
   совпадение выигрывает. В каждом правиле явно указывать `ocr` и `animated`,
   включая `false`, чтобы новая ось не попала случайно под старое правило.
3. Для новой категории или доменного профиля проверить, что matcher не скрывает
   существующую пару и не создаёт недоступное значение.
4. Поднять `version` каталога.
5. Добавить/обновить тесты загрузки и валидации, затем проверить `/formats`,
   отправку настроек и этот документ.

Профиль `animated` — зарезервированная request-scoped ось для будущего browser
маршрута. Текущие presenter и controller разрешают профили только с
`animated=false`; этот документ не объявляет отдельное публичное поле запроса.

## Владельцы и контрольный список

- Владелец схемы — backend conversion settings (`SettingsField`, каталог и
  validator).
- Владелец отображения и локального состояния — frontend CNV-92.
- Владелец обработки конкретных whitelisted ключей после очереди — соответствующий
  worker; worker не расширяет публичную схему самовольно.
- Изменение публичного поля требует синхронной правки каталога, validator,
  frontend-совместимости, queue contract и тестов. Секреты, worker credentials
  и raw engine arguments в этот контракт не входят.

Перед ревью проверить:

- `GET /api/v1/formats` содержит `settings.version`, дедуплицированные профили и
  `settingsProfile: null` там, где настроек нет;
- каждый renderer type и его границы соответствуют backend grammar;
- `editable` одинаково трактуется UI и POST validator;
- OCR не отправляет options;
- defaults и dynamic model values нормализуются сервером;
- неизвестные ключи, недоступные планы и плохие значения дают перечисленные
  machine codes;
- queue payload содержит только результат server-side validation.

Связанный внутренний wire-контракт: [`queue-contract.md`](queue-contract.md),
разделы 3 и 3.1.
